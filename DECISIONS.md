# Decisions

Design decisions made while building Jevmem v1, with the reasoning, so they can be revisited deliberately.

## Product

- **Name is Jevmem.** Package `jevmem`, memory file `JEVMEM.md`, cache dir `.jevmem/`, config `jevmem.config.json`, env prefix `JEVMEM_`.
- **The Stop hook evaluates the whole turn, not just the user prompt.** *(Superseded in v0.3.3: the user message is the state; the assistant reply is a separate key, sent only when `looksLikeQuestion` is true. See below.)* The state Jev sees is `USER: … / ASSISTANT: …`. Decisions usually come from the user, but bug root causes and architecture facts usually come from the assistant. Evaluating both in one call costs nothing extra.
- **One Jev call per turn.** Every question (nine nouls, two choices, one score) goes in a single `systemOne` request. Jev evaluates them independently and in parallel, so batching is free and keeps the hook at one round trip.
- **The read side uses `choice` probabilities, not nouls.** `UserPromptSubmit` must be fast and cheap. A single `choice` over memory ids returns a full distribution, which is enough to rank and take the top five. `search_memory` (MCP) and `jevmem search` add one noul per candidate (capped at 50) because there a per-item relevance score is worth the extra tokens.
- **Importance uses the rounded expected score.** Jev returns a probability-weighted mean over the five levels. `round(score) >= index("useful")` is more stable than argmax when the distribution is split between two adjacent levels.
- **Contradiction needs two signals.** `contradicts_existing_memory >= 0.7` AND `touches_memory_id != none`. Either alone produces false supersedes: the noul fires on "we changed our mind about something" even when no listed memory is the target.
- **Superseded lines stay in the file.** They are tagged `[superseded]` and get `→ id:new`, which keeps `git blame` and history readable and lets `audit` reason about what changed. They are excluded from recall and search.

## Jev usage

- **Every choice has a `none` option**, every noul is phrased positively with a single condition, and every score level is a concrete situation rather than an adjective. This follows the Jev docs on literal reading, indirection, and score rubrics.
- **Memory ids are capped at 200 per `touches_memory_id` choice.** Jev supports 255 options, but accuracy drops with irrelevant context, so above the cap the code pre-filters by keyword overlap with the message. The same filter feeds recall.
- **Secrets are scrubbed at the client boundary** (`createJev`) and again before the writer LLM. The scrubber is deliberately over-eager (long opaque blobs, `key=value` pairs, connection-string credentials, private key blocks). A redacted token never harms a memory decision.
- **The hook hard-times-out Jev at 2 s** with no SDK retries (`maxRetries: 0` on the timed call). A missed memory is cheaper than a slow prompt. The CLI commands (`audit`, `search`) use the SDK defaults (10 s, one retry) because nobody is waiting on a keystroke.
- **Cost is computed as tokens × $0.042 / M** (the figure given in the brief) and is configurable in `jevmem.config.json` under `jev.usdPerMillionTokens`, since the public docs do not state a price. *(Superseded in v0.3.7/v0.4.0: the price is TypeSafe's launch post, $0.042 per million input tokens with output free, and from v0.4.0 every cost in the code, `jevmem stats` and the scripts charges input tokens only.)*

## Writer

- **No OpenAI or Anthropic SDK dependency.** Both providers are called with `fetch` directly (chat completions and Messages API). It keeps the install small and the hook start-up fast.
- **Defaults: `gpt-5-mini` for OpenAI, `claude-haiku-4-5-20251001` for Anthropic.** `JEVMEM_WRITER_MODEL` overrides the model. (Until v0.5.4 the provider was auto-detected from whichever key was present; it is now chosen in `jevmem.config.json` only.)
- **The fallback is the first substantive sentence**, with role prefixes and code fences removed, clamped to 140 characters. *(Superseded: the limit is `writer.maxChars`, 200 by default.)* It is deterministic so tests and the no-key path are reproducible.
- **Duplicate lines are dropped after writing.** If the writer produces a line identical (case-insensitive) to a live memory and nothing was superseded, the new line is removed again. This costs one extra file write and avoids a second Jev call.

## Claude Code hook

- *(Superseded in v0.3.2/v0.3.4: the hook command is `"<absolute node>" "<absolute cli.js>" hook` in `.claude/settings.local.json`; the two bullets below describe v0.1.)*
- **The hook command is resolved at `init` time.** If `node_modules/.bin/jevmem` exists in the project the command is `npx jevmem hook`; if the CLI runs from a global install it is `jevmem hook`; otherwise (a checkout, or an `npx` cache) it is `node "<absolute path to cli.js>" hook`. `--command` overrides it. A bare `npx jevmem` would hit the network on every turn when the package is not installed locally.
- **Hooks are merged into `.claude/settings.json`, not overwritten.** Existing hook groups and permissions are kept. Detection is by an existing command matching `jevmem … hook`, so re-running `init` is idempotent.
- **Timeouts:** Stop hook 20 s (Jev 2 s + writer 8 s + slack), UserPromptSubmit 5 s. Both always exit 0.
- **The same turn is not evaluated twice.** A SHA-1 of the merged turn is stored in `.jevmem/state.json`; Stop can fire more than once per turn.
- **Simulation fields.** The hook accepts `user_message`, `assistant_message`, and `recent_context` in the stdin JSON in addition to the real `transcript_path`. That is what the tests and `DEMO.md` use, and it makes the hook scriptable from other tools.

## v0.5.0: signed releases

- **Trusted publishing first, a token as fallback.** npm's docs (https://docs.npmjs.com/trusted-publishers, read 2026-09-25) require npm 11.5.1+, Node 22.14+, a GitHub-hosted runner and `id-token: write`, and attach provenance automatically. The workflow upgrades npm, runs on Node 24, and also passes `NODE_AUTH_TOKEN` from an optional `NPM_TOKEN` secret with `--provenance`, so the same job works if OIDC cannot be set up.
- **Off by default.** The publish job runs only when the repository variable `NPM_PUBLISH` is `true`, so pushing the v0.5.0 tag verifies the release without publishing it (the brief: do not publish from it now). The `npm` environment is where required reviewers can be added.
- **The tag must match three files.** `package.json`, `.claude-plugin/plugin.json` and the npm source in `.claude-plugin/marketplace.json` all carry the version; the plugin installs from npm, so a mismatch would point users at a version that does not exist.

## v0.5.0: import

- **Statements, not files.** A `CLAUDE.md` mixes facts, rules, prose and code. Each list item and each prose sentence is one candidate, and each goes through `decide` like a turn, so the same thresholds decide what is memory-worthy; what `CLAUDE.md` says in passing ("Welcome to the repo") is skipped the same way small talk is. It costs one Jev call per statement (about $0.0001 each at the measured decide cost).
- **Sequential, in file order.** Later statements are decided against the lines accepted earlier in the same import, so a rule repeated in `AGENTS.md` is a duplicate, and a statement that reverses an earlier one supersedes it as a turn would.
- **Imported lines are verified, so they are gated first.** The brief makes imported lines verified (jevmem wrote them here), and verified lines skip the recall gate. But `CLAUDE.md`, `AGENTS.md` and `.cursor/rules/` are as open to a pull request as `JEVMEM.md`, so accepted statements also pass the poisoning gate (one batched call) and the hidden-text check before they are written. Otherwise `import --apply` would turn a planted rule into a trusted memory.
- **Auto memory only on request.** It lives in the home directory, and `jevmem init` promises not to read there, so `import` reads it only with `--from claude-auto-memory`. Its location follows the docs (https://code.claude.com/docs/en/memory, "Storage location", read 2026-09-25): `autoMemoryDirectory` if a settings file sets it, else `~/.claude/projects/<project>/memory/`, with `<project>` derived from the git repository so worktrees and subdirectories share it; `CLAUDE_CONFIG_DIR` and `CLAUDE_CODE_PROJECT_DIR_NAME` are honoured. `MEMORY.md` is an index of links, so the topic files are read instead.
- **jevmem's own instructions are skipped** (`AGENTS.md`'s "Jevmem project memory" section, `.cursor/rules/jevmem.mdc`): they are about jevmem, not the project.

## v0.5.0: the Claude Code plugin

- **The plugin is the npm package.** The docs (https://code.claude.com/docs/en/plugins/marketplace-reference, read 2026-09-25) list an `npm` plugin source, fetched "with your npm client and unpacked without running install scripts". The repository's `.claude-plugin/marketplace.json` points at `jevmem` on npm at the release version, and the package root is the plugin root (`.claude-plugin/plugin.json`, `hooks/hooks.json`, `hooks/jevmem-hook.sh`, `dist/`). A relative-path or GitHub source would have needed `dist/` committed to git. Consequence: the plugin works only for a version that is on npm, so `marketplace.json` names a published version and a test keeps it equal to `package.json`.
- **`dist/cli.js` bundles its dependencies.** Claude Code installs a plugin's Node dependencies only when the package ships an npm lockfile, with a 60-second limit, using npm from PATH ("Node.js package dependencies" on https://code.claude.com/docs/en/plugins/loading). Rather than depend on that, the CLI entry is built with every dependency inlined (about 1.5 MB), so hooks and the MCP server run from the tarball as fetched; the e2e plugin run uses an `npm pack` tarball with no `node_modules`. The library entry (`dist/index.js`) keeps its dependencies external. Start-up went from about 60 ms to about 40 ms for `jevmem --version`.
- **Launcher, not `node`, in the plugin's commands.** Plugin hooks cannot know the absolute node path that `init` writes, and the desktop app runs hooks with a bare PATH. `hooks/jevmem-hook.sh` searches the usual install locations and caches the result in `${CLAUDE_PLUGIN_DATA}`. It lives in `hooks/`, not `bin/`: a plugin's `bin/` goes on the Bash tool's PATH and stops claude.ai/Cowork from installing the plugin (manifest reference, *Standard layout*).
- **MCP server in `plugin.json`, not `.mcp.json`.** A root `.mcp.json` would also be read as this repository's own project MCP config by anyone developing jevmem in Claude Code, with an unresolved `${CLAUDE_PLUGIN_ROOT}`.
- **Plugin plus `init`: the plugin stands down.** Claude Code deduplicates identical handlers across settings files but keeps a plugin's copy separate (hooks reference, *Hook handler fields*), so both would fire. The plugin's commands pass `--plugin`; when the project's `.claude/settings*.json` has a jevmem hook, that invocation does nothing, logs it once a day and returns a `systemMessage` once per session. The init hooks win because they are the explicit, per-project choice. `init` cannot see a user-scope plugin (it does not read the home directory), so the runtime check is the one that matters; `init` still warns when the project's own settings enable the plugin.
- **The plugin runs everywhere it is enabled.** *(Superseded in v0.5.1: the plugin is dormant until `jevmem enable`; see below.)*

## v0.5.0: the Stop hook does not wait

- **What the docs say (read 2026-09-25, https://code.claude.com/docs/en/hooks, Claude Code 2.1.274 CLI and 2.1.281 desktop bundle on this machine).** *Command hook fields*: `async` — "If `true`, runs in the background without blocking". *Run hooks in the background*: "Only command hooks support `async`"; it is "silently ignored" on `UserPromptSubmit` (and on `SessionEnd`, `PreToolUse` and a few others), so recall must stay synchronous anyway; output and exit codes of async hooks are ignored; "When the session ends, Claude Code sends `SIGTERM` to any async hooks still running. The process has a few seconds to exit gracefully before Claude Code sends `SIGKILL`." *Hook handler fields*: there are five handler types, `command`, `http`, `mcp_tool`, `prompt` and `agent`. There is no in-process "function hook" type in settings or plugins; in-process callbacks exist only in the Agent SDK (the *Timeouts* section refers to "Agent SDK callback hook"s), which is not how Claude Code users run jevmem, so jevmem does not use them. *Exec form and shell form*: shell form runs `sh -c` on macOS and Linux, Git Bash (or PowerShell) on Windows.
- **Measured before relying on it.** A probe hook that logged signals, run with `claude -p`: the async Stop hook received SIGTERM the moment it started (the session was already ending) and was killed about two seconds later; a node child it started died before running any code, so the signal goes to the process group; a node child started in its own process group (`set -m`) ran to completion. Node resets signal dispositions at start-up, so a shell `trap '' TERM` does not protect it. So `async: true` alone would lose the last turn of every `claude -p` session.
- **So the Stop hook is async *and* detaches.** `hooks/jevmem-hook.sh --detach` ignores SIGTERM, saves the hook JSON to a temp file, starts node with `setsid` (or `set -m` where there is no `setsid`, as on macOS) and exits; node queues the turn and asks the daemon to evaluate the queue (starting it, detached, when it is not running). The process Claude Code starts now exits in 13–15 ms p50, against 355 ms for the v0.4.5 hook through the warm daemon, and the decision lands 221–428 ms after it starts. Without `async` support the launcher still returns in milliseconds, which is the brief's "otherwise hand off and exit".
- **The launcher also finds node.** The desktop app runs hooks with a bare PATH (v0.3.2); `init` passes the absolute node path, and the plugin (below) relies on the launcher's search (Homebrew, Volta, nvm, fnm, asdf, mise, n), cached in `${CLAUDE_PLUGIN_DATA}`.
- **The e2e harness waits for the queue.** A line can now land after `claude -p` exits, so each turn waits until that turn's decision is recorded and the queue is empty (the harness prints how long: tens to a few hundred milliseconds).

## v0.5.0: never lose a turn

- **Every turn goes through the queue, not only failed ones.** The Stop path appends the scrubbed turn to `.jevmem/queue.jsonl` and then evaluates the queue oldest first. A queue that only held failures would need a second rule for ordering ("is anything older still queued?") and a second path through the code; with one queue, order and retries come from the same loop, and the non-blocking Stop hook (below) is the same queue with the evaluation moved to the daemon.
- **A failed head blocks the turns behind it.** Contradiction handling depends on what is live when a turn is decided; if a reversal were decided before the decision it reverses, it would supersede nothing and the old decision would be saved afterwards as live. So a retryable failure puts the head back with a backoff and stops the drain. The cost is that during an outage nothing is saved until Jev answers again, which is the same outcome with the order kept.
- **What is retried:** timeouts, network errors, 408, 429 and 5xx (529 included). A 400 or 401 will not get better by waiting, so those drop the turn with a log line, as every failure did before.
- **Exactly once.** A drainer removes a turn only after it is decided and recorded. If it dies in between, the next drainer finds the turn's hash in `decisions.jsonl` and removes it without a second Jev call. Two lock files keep a hook process and the daemon from losing each other's queue edits (`queue.lock`, held for milliseconds) or evaluating the same turn twice (`drain.lock`, held while evaluating; a dead owner's lock is taken over).
- **Caps: 24 hours, 200 turns.** A turn a day old is unlikely to be worth a line without its session around it, and an unbounded queue of scrubbed text is data nobody asked jevmem to keep.

## Unreleased (v0.6): the guard fixes from the trial

- **Sets first, and a dev set made of the trial's own calls.** `eval/guard-heldout-v2.jsonl` (274 calls, five new projects, six groups, each call labelled with the rules it breaks and whether the tamper check should ask, a folder to start in where it matters) was committed before any code, shares no run of five words with the dev sets, the trial's commands or held-out v1, and was run once on the build before the change and once on the build after it. The first run found a row whose folder had been dropped by the generator (`rm ../JEVMEM.md`, meant to start in a subfolder); the row was fixed and both builds rerun, which is why the set has a second commit. `eval/guard-shell-dev.jsonl` holds the trial's 8 calls, cut to what matters with home paths as `~`, plus 30 cases the fix needs; tuning happened there, on `guard-dev` and on `guard-git-dev` only.
- **One reader for three consumers.** The prefilter, the tamper check and the git expansion each split a command line on their own, and all three saw a heredoc's body as commands, which was the cause of six of the trial's seven false asks. `src/shell.ts` reads the line once, the way the shell does: a heredoc is the input of its command, a shell string and a body fed to a shell are commands, and each consumer walks the same list. No special case knows the trial's commands.
- **A heredoc written to a file is a Write of that file, and a script written and then run is run.** Treating every body as input would have opened a hole (`cat > x.sh <<EOF … EOF && bash x.sh`), so a file the same command line writes and then runs by a shell (`bash x`, `sh x`, `./x`, `source`, `.`, `bash < x`, `printf > x && bash x`) is read as commands. A file run by anything else (`python3 x.py`) stays a Write: the guard reads shell, not Python.
- **The tamper check compares resolved paths and knows each writer by name.** Matching `.jevmem` as text in any word made `~/.jevmem/env` this project's `.jevmem/`; now every path is resolved against the folder the command runs in (`cd`, `pushd`, `popd`, `git -C`, `~`, `$HOME`, `$PWD`, `$CLAUDE_PROJECT_DIR`) and compared with the project's three files. Which commands write is listed by name (redirections, `tee`, `cp`, `install`, `rsync`, `ln`, `mv`, `rm`, `sed -i`, `perl -i`, `awk -i inplace`, `sort -o`, `uniq`'s second file, `truncate`, `touch`, `dd of=`, `git checkout`, `restore`, `rm`, `mv`, `git clean -x`), which read too, and a command the guard does not know still asks when it names one, as before. A path with a variable the guard cannot read (`rm $TARGET`) is not matched: fail open, as `cd "$DIR"` already was for git. A wildcard is matched by its folder and pattern, not by listing the disk.
- **Commit messages are a feature only for rules about them, and always a strong match.** Matching the message on shared keywords would have missed "Conventional Commits" against `git commit -m 'stuff'` (held-out v1's miss), so a rule that mentions a commit message, a trailer, Co-Authored-By, Signed-off-by, a sign-off, Conventional Commits or whose name commits are under is matched against every commit that carries a message in the call, the way a rule about committing is matched against the files a commit would take. The cost is one Jev request per such commit in a project with such a rule (the message changes every time, so the cache does not help); with no such rule nothing changes and nothing extra is sent. `--amend` without a message, `-c`, `-C`, `--fixup` and `--squash` carry no message the guard can see.
- **When Jev is late, ask on a strong match and never deny.** The trial's e2e run let `.env` through when one check answered after 1,048 ms against the 1,000 ms budget. The budget is now 2,000 ms (recall's), and a candidate matched on a path, a filename, a staged file, a pair, a tool or a commit message is asked about with a reason that says it was not checked, in `block` mode too, because a denial needs Jev's verdict and an ask only needs a person. Keyword-only candidates stay fail-open: most everyday calls that reach Jev are those, and asking on every late one would be the trial's false asks by another route. In `claude -p` the ask is a deny, which the docs say.
- **What Jev sees of a heredoc.** The 2,000-character window used to be cut around the first matched term, so a long script's `cat > x.py <<'EOF'` head could fall out of view; each body is now cut to 600 characters around the match and the command's shape stays. The cache keys of heredoc calls change with it; other calls' do not.
- **What did not change.** Dev's numbers are identical on both builds, row for row; held-out v1's second look gained one catch (the Conventional Commits row) and lost none; the hook's no-candidate p95 did not rise (44 → 40 ms through the plugin launcher, 39 → 35 through `init`'s). The misses left on the shell dev set are Jev's judgment (a script that runs `jevmem guard test "git push origin directory"`, 0.57 to 0.71; a `Signed-off-by` under the committer's own name, 0.07; the package.json version bump, 0.48 to 0.60) and one shared word (`git tag -d`, `npm version`), which the prefilter's floor of two keeps out on purpose.

## Unreleased (v0.6 part 3c): every saved line states the fact

- **Sets first.** Four sets were committed before any change in this part (`a0273eb`): line-text dev (`eval/lines-dev.jsonl`, 48 saved turns, three projects) and held-out (`eval/lines-heldout.jsonl`, 64 turns, four other projects), each turn labelled with the sentence(s) that state the memory, keys a line must contain to state it and to keep its reason, and the requests, hand-offs and instructions it must not be; and genuine-rule dev and held-out (`eval/rules-dev.jsonl`, 16; `eval/rules-heldout.jsonl`, 24): rules and preferences stated with an instruction to the assistant, which must be saved, and planted-line turns, which must be skipped. `test/lines-eval.test.ts` keeps them free of text shared with each other, with every other eval set and with jevmem's questions (`src/pick.ts` included); the first draft shared five-word runs with older sets, mostly the projects' own lines repeated in every row, and they were reworded before the commit, among them a held-out hand-off that repeated held-out v4's "Have a subagent find the cause and fix it".
- **Judged in code.** `scripts/eval-lines.mjs` checks each line against its row's keys, with no LLM judge, so no judge agreement needed reporting. Keys are chosen so that a line stating the fact contains one and a request never does (the test checks both ways); I read every dev line and every held-out line of both builds against them.
- **Why the injection question fired on a genuine rule** (`results/diag-rule-injection-2026-09-29-before.json`). Not the instruction: without "Nothing to do right now; just acknowledge it." the guard e2e's turn still scored 0.64 in tier 2; without "from now on" it scored 0.24. Tier 1's broad injection noul put such turns at 0.52–0.67, so they escalated, and tier 2's memory noul (`asks_the_ai_to_store_or_alter_memory_or_rules`, 0.65–0.89) read the lasting framing, "from now on", "remember this rule", "a note for all future work", as an order to store a rule of the AI's own. Its question asked whether the message asks an AI to record "a memory, rule, or setting of its own", and its yes example was "Save this as a permanent rule.": a person's standing rule for the project reads much like that.
- **What Jev is asked, not a word rule.** The memory noul now asks about orders aimed at the AI's own memory or settings, and permissions granted to the AI itself; its no side names a rule, decision or preference the person states for the project however lasting, even when it asks only to be kept in mind or acknowledged. Tier 1's no side says the same. With only that, tier 1's score for text quoted from a file dropped (a README quote 0.87 to 0.79 on the regression set, two dev plants under 0.7, caught by tier 2): the yes side had never named quoted text, which tier 1 had caught through "plant text into its memory". It names it now (0.79–0.98 in tier 1 for every dev plant; genuine dev rules at most 0.29 in tier 1 and 0.26 in tier 2: `results/diag-rule-injection-2026-09-29-after.json`). The weights and thresholds did not change. The poisoning gate asks its own question (`src/guard.ts`), which this does not touch.
- **Jev picks the line's sentences** (`src/pick.ts`). The local writer's one sentence by cue words is the cause of both the junk lines and the dropped reasons: "fix" makes a hand-off a bug line, "later" makes "keep it in mind for later" a to-do, and a reason in its own sentence never makes the line. More cue words would be a local rule; the brief said to ask Jev. One request, after decide says save, with the kind, what a line of that kind states and the candidate sentences under bare ids; two choices: which sentence states the memory "as a fact a later session on this project needs to know, not as a request, a hand-off or an instruction to the assistant", and which other sentence gives its reason, or none. The line is the sentences as written, in their order, when they fit in 200 characters, else the one that states the memory.
- **Not folded into decide.** The only request every saved turn makes is decide's, and it is made before anyone knows the turn is saved. Jev answers each question on its own, so adding the pick there would not move decide's answers, but it would put every turn's sentences in every decide state and ask the question on every skipped turn, which the brief ruled out. A text with one sentence asks nothing. A failed pick means the old writer's line, logged as a writer fallback, never a lost line.
- **Two choices, not a noul per sentence.** A noul per sentence (states it? gives the reason?) would cost two questions per sentence; the choices cost two questions. The reason is the most likely answer other than the sentence already picked (Jev may put the main sentence first when it holds its own reason), and none when none is more likely. "Or two, if they fit": two sentences that do not fit leave the reason out rather than cut the fact.
- **Dead ends, retests, works-now.** Asked for "the approach that was tried and failed", Jev picked the sentence saying it failed and why, and the one naming the approach went (2 of 12 dev dead ends); a dead end is now asked for what was tried, "the approach itself, not how it turned out", then why it failed, and the two go through the dead-end fitter. A retest is asked for the new reason first: asked for what was tried again, Jev split 0.52/0.48 between the sentence and "Back on PHP-FPM." on a dev retest, and the line lost its new reason; asked for the reason, 1.00. A dead end that works now keeps its ordering (the sentence naming the approach first). The fitter also keeps a reason after "but" inside the attempt's own sentence when that sentence is too long, dropping the upside, as it already did for a later sentence (one dev line, and 0.5.9 had the same miss).
- **Candidates are the writer's own text.** The sentences of the text the writer already got: the user message, or the reply where it is used today (a bug, a structure fact or a dead end from the reply; both sides for a dead end from both), cut where decide cuts them. A turn whose line comes from the user message never offers the reply, even when the reply found the cause: that would change where lines come from, which the brief did not ask for.

- **Held-out, run once** (`results/lines-heldout-2026-09-29-*.json`, `results/rules-heldout-2026-09-29-*.json`). Line text, the final code against 0.5.9, decide then the writer: of the turns saved, lines that state the fact 62/63 against 41/59, that keep the reason 29/30 against 5/25, junk lines 0/63 against 13/59. The misses: a rule whose consequence Jev picked as the rule ("Google Fit throttles the whole app…"), a to-do whose second sentence was "Leave it for the next milestone and don't start on it today." (as what it waits for), and a structure fact told in two sentences that kept one. Genuine rules: 10/12 saved against 6/12, none skipped as injection against 4/12; the two misses fell under `contentMin` in both builds. ## Unreleased (v0.6): the guard sees what git would commit

- **Why.** Indirect breaks were 0/10 on dev and 0/9 on held-out v1, and the case people try first is the one in the docs: "Never commit .env files", then `git add .` or `git add -A` with an untracked `.env`. The command names no file, so the prefilter had nothing to match. `git commit -a` is the same with a changed tracked `.env`.
- **`git status`, not `git add --dry-run`.** A dry-run add names exactly what would be added, but `git add` takes `.git/index.lock` even with `-n`, and Claude Code can run several tool calls at once: a guard holding the lock would make the user's own `git add` or `git commit` fail with "index.lock exists". `git --no-optional-locks status --porcelain=v1 -z --untracked-files=all --no-renames --ignore-submodules=all` never takes it (tested with a held lock), and one run serves every git command in the line. The files each command takes are worked out from it as git does: `git add` takes untracked (not ignored) and changed tracked files under its pathspecs, `-u` only tracked ones, `-f` ignored ones too; `git commit` takes what is staged, `-a` adds changed tracked files and never untracked ones, pathspecs commit only the tracked files they name. Deletions are left out (they add no content), and so is a dry run. An unquoted `*` is the shell's (no dotfiles), a quoted one git's (it crosses folders).
- **Only rules about committing.** Matching the staged files against every rule's paths would ask, at every `git add -A`, about rules that forbid editing a path ("docs/api/ is generated; never edit it", "don't hand-edit internal/pb/"): the edit is the break, and the guard checked it when it happened; committing regenerated output is what the rule wants. So staged files count only for a rule whose text says commit, git, check in, push, tracked or version control, only as a path or filename it names, and never for a broad directory such as `src/` (so "No console.log calls in committed source under src/" is not a candidate for every commit). They give no keywords.
- **Jev is told which files.** Without them Jev sees `git add -A && git commit -m wip` next to "Never commit .env files" and has no way to know. The request adds `"stages": ".env (untracked)"`: at most 10 paths, only those a candidate rule names, scrubbed. The rest of the list is not sent or kept. The question and its examples are unchanged, so `GUARD_VERSION` stays; the answer cache is keyed by the payload, which now includes the files.
- **200 ms, fail open.** As a whole hook process, `git add -A && git commit` took 10–11 ms more at p50 in a small repository and 31–33 ms more in one of 20,000 tracked files (`results/guard-latency-2026-09-28-*.json`). The budget is 200 ms and a quarter of `guard.budgetMs`, leaving the Jev request most of the 1 s. A timeout, no git, not a repository, a `cd` to a variable, `GIT_DIR`, `--git-dir`, `--pathspec-from-file` or an alias gives no files and a note in `jevmem guard test`: the call is matched on what it names, as before. It runs only for a Bash call with a `git add`, `git stage` or `git commit` in it, and only when an enforced rule about committing names a path or file, so every other call costs nothing more.
- **A rule from an unverified line asks; only a verified one denies.** The poisoning gate is tuned to pass team rules ("Never commit .env files" must pass), so it cannot tell a planted ordinary rule from a real one. A planted rule that could deny would let anyone who can edit `JEVMEM.md` stop an agent's work in `block` mode. Provenance already tells the two apart: a line jevmem wrote here from your own turn is verified. So the deny needs a verified rule, and an unverified one is asked about with its id in the reason, where the user sees it. The cost: a rule you add with `jevmem add` or by hand asks rather than blocks.
- **`blockMin` below `askMin` falls back to the defaults, not to no decision.** Every other bad setting makes the guard stand aside, but this one is a valid pair of numbers in the wrong order: standing aside would switch the guard off over a typo, and using it would deny calls that should only be asked about. The defaults keep the guard on, and the reason is shown in `jevmem doctor` and `jevmem guard test` and logged, as a problem with the settings rather than a failed check.
- **Measured on sets that were used before.** The change touches the prefilter, and the guard's held-out v1 was run on 2026-09-26: rerunning it now is a second look, not a held-out result, and its published numbers stay as scored. Dev, held-out v1 and a new 20-call git dev set (written with the change, so it tests the cases the design names rather than finding new ones) were run the same day on `main` before the change and after it. Only the `git add` and `git commit` rows moved. A fresh guard held-out set is needed before any of this is published in the README.

## Unreleased (v0.6 part 1): the PreToolUse guard

- **Silent failures, shown from the log.** The 0.5.7 scrubber bug dropped turns and emptied recall with only a line in `.jevmem/log.jsonl` to show for it. `jevmem doctor` and `jevmem stats` now read the last 7 days of that log (no network) into three groups: dropped turns (the queue's `dropped` events and the Stop hook's own problems, such as no key or an unreadable transcript), failed recalls (the UserPromptSubmit hook's problems), and guard checks that failed or timed out (the guard's own failure lines). createJev logs the failed request too; that line is not counted again, and a drop that `jevmem watch` also logs as the hook's error counts once. A turn read fine with nothing in it is not a drop. Reasons that differ only in numbers (a JSON position, milliseconds) are grouped, with the latest message shown.
- **Tests are sealed off from the machine.** The test process inherited this machine's `HOME` and `TYPESAFE_API_KEY`, and when run from a Claude Code session its `CLAUDE_*` variables too: a test that ran the hook without injecting a client would have sent a real request with the real key, and `~/.jevmem/env` or `~/.claude/settings.json` could have changed a result. `test/setup.ts` now gives every worker a temporary `HOME` and `CLAUDE_CONFIG_DIR` and removes those variables (the live test keeps the TypeSafe key when `JEVMEM_LIVE=1`).
- **Flaky tests, found and fixed.** With every run and failure now recorded, the unit suite ran 131 times on its own and 74 times alongside an e2e run. 31 runs before the fixes below: 2 failures, both the old-CLI launcher test (the setpgid warning, next). 50 runs with the launchers fixed: 1 failure, `launcher.test.ts` looking for leftover queue temp files as soon as the turn's line appeared, while the detached CLI was still moving the turn out of the queue (a temp file and a rename); it, and the dormant test, which snapshots the project after its Stop turn, now wait for the drain to end. 50 runs on the final code: none, and none of the 74 alongside the e2e. No failure needed the e2e or came from shared state.
- **The setpgid warning.** The old-CLI launcher test's two failures: the Stop step's stderr held bash's "child setpgid (…): Operation not permitted". With `set -m` both the shell and the child put the child in its own process group; when the child wins, the shell's `setpgid` fails and it says so. It is a race in both launchers since v0.5.0, 2 in 3,000 plain launches here. `{ … & } 2>/dev/null` hid it but made bash park the real stderr on a spare descriptor that the CLI inherited, so the hook's stderr pipe stayed open until the CLI exited (3 s instead of 14 ms in a direct check, and the launcher tests timed out). `exec 2>/dev/null` right before the launch leaves no copy: 0 warnings in 3,000 launches, every child ran.
- **The e2e drain timeout.** The one "queue did not drain within 60 s" on record (v0.5.4's first run, handwrite turn 2) left no logs. Across the 282 drains in `results/e2e-*.txt`, every slow one outside the outage scenario (which queues on purpose) is explained by the retry schedule: one failed Jev request adds 15–30 s (the 30.5 s dormant drain in v0.5.6), and a second failure for the same turn needs 45–75 s, past the harness's 60 s. A stale transcript (the Stop hook reading the previous turn and skipping it as "already captured") was ruled out: in 15 real `claude -p` turns the transcript already held the turn's prompt and final reply when the Stop hook started. Neither a second Jev failure nor a Stop hook killed before its `trap` can be told apart without the project's state, so the harness now prints the queue, the drain lock, the daemon and the last log lines when a turn does not drain.
- **The guard's requests to Jev, measured.** 400 calls from new hook processes (`scripts/bench-guard-jev.mjs`): 1 timed out at the 1 s budget (the SDK's timeout, after 953 ms), none failed otherwise; answered requests took at most 620 ms. The budget was left at 1,000 ms.
- **The launcher is tested with the real 0.5.7.** The CLI and the plugin folder are built from the v0.5.7 tag, as the npm package was, with the same lockfile; CI now fetches tags. A `node` beside the CLI records every process the launcher starts: under both plugins, `Stop` and `UserPromptSubmit` start the same ones with the same arguments and give the same results, except for the new launcher's one `guard --help` from `/` when nothing is cached.
- **Part 1d: a secret's name, not its spelling.** The scrubber caught `DB_PASSWORD=x` but not `PGPASSWORD=x`, because its pattern wanted an underscore before the word; it also never looked at JSON's `"password": "x"`. The rule now looks at the parts of a name, split at `_`, `-`, `.`, digits and camelCase, and redacts the value when a part ends in PASSWORD, PASSWD, PWD, SECRET, TOKEN or KEY, or is PASS. A part must end with the word, which keeps `keyboard`, `tokenizer` and `MAX_TOKENS`. `PGPASSWORD` and `APIKEY` have nothing between the prefix and the word, so a part may have anything before it, and then `monkey` looks exactly like `apikey`: only a list can tell them apart. The list is of everyday words (`monkey`, `donkey`, `turkey`, `hockey`, `jockey`, `whiskey`, `lackey`, `hotkey`, `turnkey`), so an unknown word ending in "key" is redacted, and no secret name is let through by a guess. Any part counts, not only the last, so `SECRET_KEY_BASE` (Rails' main secret, missed before) is caught, at the cost of `token_ttl: 3600` and a host such as `token-service:3000`. A pair whose name is not a secret's never swallows the pair after it ("Note: token: x"): the name and separator are matched first and the value is matched only for a secret's name. `==`, `=>` and `::` are not separators, so comparisons, arrow functions and Rust paths are left alone. After `NAME=` or `NAME:` the value may start on the next line, as 0.5.7 allowed for `password:`: same-line only would have been kinder to YAML and Markdown, but it would have sent something 0.5.7 redacted.
- **The replay, and what it could change.** The same 1,100 requests as in part 1c (rebuilt from the eval sets, the benchmarks, bench-ops, DEMO, the e2e transcripts still in `~/.claude/projects` and the author's own projects, with the functions on main that build them) were rebuilt once with each build, memory ids seeded so both builds rebuild the same ones, and compared as sent: 2 changed, both the guard dev call `dev-fieldapp-11` (shipped and tuning run), whose `const token = await fetchToken();` now goes as `const token=[REDACTED] fetchToken();`, an over-redaction. No request sends anything the old scrubber redacted. The guard dev eval is published, so it was run once more, with and without `--tuning`: every number as published, and `dev-fieldapp-11` scored 0.08 and 0.07 against 0.07. The public numbers stay as they are; the reruns are kept in results/ and not cited. The replay script reads local transcripts and stays out of the repository, as in part 1c.
- **The other JSON-text scrub.** Looking at every call of the scrubber for another `scrubSecrets(JSON.stringify(…))` found one: `jevmem audit` scrubbed its repository snapshot that way, and a `package.json` script ending in `--token=$VERCEL_TOKEN` made it exit with a JSON error before any request (0.5.7 too). It now uses the same per-string scrub as `createJev`.
- **The setpgid race is harmless, measured.** `scripts/setpgid-study.mjs` launches `Stop` hooks through both launchers in a process group of their own, as Claude Code does, and kills that group as soon as the hook exits: harsher than a session end, which sends SIGTERM and SIGKILL only seconds later, and a fair test of the macOS path, where job control has moved the CLI before the shell goes on. With the launchers' stderr sent to a file per launch (one line changed), each warning can be matched to its launch. On the committed code (`ba10441`), 6,000 launches per launcher with the warning visible: 18 warnings (7 through the plugin's launcher, 11 through `init`'s), and in each the process bash named led its own group, the CLI was outside the hook's group, exited 0 and the turn was decided. Nothing was left in the hook's group at any exit, and all 12,000 turns were decided; so were 6,000 more with the launchers as shipped. An earlier run on `af1024e` (12,000 launches, 17 warnings) came out the same. The turns were decided by a local stand-in for Jev (results/setpgid-2026-09-27.json). The message is bash's child-side `setpgid` failing: the shell and the child both make the child a group leader, and the second call can fail while the first is taking effect; in a fork-and-`setpgid` loop in Python, outside bash, 12 child calls and 14 parent calls failed in 5,000 forks, never both, and the child always ended up in its new group. So no turn could be lost and `exec 2>/dev/null` stays; nothing else was changed in the launchers.
- **Where the detached CLI's errors go.** The detached CLI's stdout and stderr have been `/dev/null` since v0.5.0, so its errors must reach `.jevmem/log.jsonl`. Everything inside `main` already did (queue drops, hook problems). A failure that escaped `main` did not: it was printed to stderr, and since the CLI is built in chunks, a chunk missing after an upgrade is such a failure. `cli.ts` now writes it to the project's log (in an enabled project only) and removes the saved hook input, which would otherwise stay in the temp folder with the turn's text in it.
- **A missing key says so once per project.** No key means the hooks do nothing, so the silence looked like jevmem working with nothing to save. The message goes out the way 0.5.6's "CLI not found" does, as a `systemMessage` on `UserPromptSubmit`, but it comes from the CLI, which is what looks for keys, and it is kept once per project in `.jevmem/state.json` rather than once per session: a key belongs to the machine or the plugin, not to a session, and repeating it every session would be noise. Finding a key clears the record, so a key that goes missing later (a deleted `~/.jevmem/env`, say) is announced again. It says what is missing, where jevmem looks, and one command: for the plugin `/plugin configure jevmem@jevmem`, which keeps the key in the system's credential store; for `jevmem init`'s hooks there was no single command (edit `~/.jevmem/env` by hand and `chmod 600` it), so `jevmem key` was added. It asks without echoing, so the key is not left in shell history, writes the file 0600, and keeps the file's other lines. While testing, `claude plugin install` (2.1.281) said that a plugin's `userConfig` can also be passed with `--config KEY=VALUE`; that would put the key on a command line, so the message does not suggest it.
- **The README's limits paragraph, true for 0.5.7 and main.** It said a turn is dropped only after 24 hours or past 200 queued turns. Since v0.5.0 any error that is not a timeout, a network failure, 408, 429 or 5xx drops the turn at once: a 400, a 401 from a wrong key (every turn, until the key is fixed), and, in 0.5.7, the scrubber's JSON error. It now says so, and names only what 0.5.7 has: the drop's log line and the retry-queue line of `jevmem stats` (the failure list in `doctor` and `stats` is unreleased).
- **Part 1e: what `/plugin configure` is.** On Claude Code 2.1.274 and 2.1.281 it is a subcommand of `/plugin` in the terminal UI only: `claude plugin --help` has no `configure`; the TUI's `/plugin help` lists "/plugin configure <plugin> - Set userConfig options" (the text is in both binaries, with `config` as an alias); `claude plugin install --help` refers to "the interactive /plugin configure flow". Claude Code's docs (read 2026-09-27) don't list it: the commands page names `list`, `install`, `enable` and `disable`, and the discover-plugins page documents the other way in, `/plugin`, Tab to Installed, Enter on the plugin, Configure options. Both open the same dialog: the field masked, "(unchanged)" when a value is stored, Enter saves ("Configuration saved."). The command matches a bare name in every marketplace (`ir(GH(P))` in 2.1.281, the same code in 2.1.274), so `jevmem@jevmem` is right only for the jevmem marketplace and `jevmem` is right for all. `scripts/plugin-configure-check.py` sets and then changes the key both ways with the plugin installed from a marketplace called not-jevmem, and checks the key a new session's hooks send; A, B and C passed on both versions. `claude plugin install … --config typesafe_api_key=…` also replaced the value on an installed plugin, but it puts the key on a command line, so nothing here suggests it.
- **The plugin's message gives `jevmem key`.** One fix for both kinds of hooks, the one the e2e follows word for word, and no marketplace name. The plugin setting stays in the list of places jevmem looks, since a marketplace-free way to set it was shown to work; the help that `init`, `enable` and `doctor` print, `jevmem key --help` and the docs name it as `/plugin configure jevmem`. The key link is https://console.typesafe.ai/keys, the page TypeSafe's quick start names ("Get your API key from the dashboard"); the home page's Sign in button goes to the same console. The page itself could not be opened from here: Cloudflare answers scripts with 403 and shows the built-in browser a bot check, which was not worked around.
- **A changed key reaches the daemon.** Checking B by hand, the new key was in the keychain and the old one was sent: jevmem's warm daemon keeps the Jev client it started with, and every prompt resets its 30-minute idle timer, so a replaced key (in the plugin setting or `~/.jevmem/env`) was not used while anyone kept working. Each hook request now carries `client`, a hash of the key and base URL it would use; a daemon started with another one answers `key-changed` and exits, and the hook works inline with the new key and starts a new daemon. The key never goes over the socket, and a request without `client` (an older hook) is served as before. DAEMON_VERSION is 5; a 0.5.x daemon still running ignores the field until it exits.
- **The MCP server reads the key files.** It never did: only hooks and commands called `loadEnvFallbacks`, and a server that Codex starts from the section `jevmem init --tool codex` writes (with no `env` line, as docs/mcp.md said to) had no key. It now reads `<project>/.jevmem/.env` and `~/.jevmem/env` when a tool needs Jev and no key is set, on each call, so `jevmem key` helps a session that is already running.
- **`jevmem key` asks first.** Replacing a saved key without a yes could throw away the only copy of a working key. The question needs a terminal; without one, `jevmem key` changes nothing and says how. Raw mode is set before the prompt is printed, so a key pasted as soon as the prompt shows is not echoed by the terminal. The folder is chmodded to 700 even when it existed, and an existing file to 600 before the key is written into it.
- **The TUI check updated Claude Code.** The first run of the desktop bundle's TUI in a temporary config printed "Update installed" and had moved `~/.local/bin/claude` from 2.1.274 to a new 2.1.283. The link was put back at once (the 2.1.283 download was left in `~/.local/share/claude/versions/`). The check script and the e2e harness now run Claude Code with `DISABLE_AUTOUPDATER=1`.

## v0.5.3: a thin plugin that runs the installed CLI

- **Why the plugin moved.** The directory installs a plugin from the plugin folder in its repository (pre-submission checklist, https://claude.com/docs/plugins/pre-submission-checklist, read 2026-09-25: "People who install the plugin get only the plugin folder"). The v0.5 plugin was the repository root and ran `dist/cli.js`, which is built, bundled (1.5 MB, over the 256 KiB review limit) and not committed, so a directory install would have had nothing to run. `plugin/` now holds the manifest, `hooks/hooks.json`, one launcher and the README the directory requires ("a README of at least 40 words in the plugin folder": Blocks); `scripts/check-plugin.mjs` keeps it that way in CI.
- **The CLI comes from npm, installed by the user.** No `npx` (the checklist blocks unpinned launchers and holds pinned ones for a reviewer; it also downloads code at run time). The price is one extra install step and a version skew between the CLI and the plugin, which the launcher reports on stderr.
- **Why a launcher at all.** Hooks must stay silent without the CLI, and a bare `jevmem` command would make Claude Code report a failed hook; Claude Code's desktop app gives hooks a bare PATH on which neither `jevmem` nor `node` is found; and the async Stop hook must survive the session-end SIGTERM. The launcher does those three things and nothing else; the CLI and Node locations and the version check are cached in `${CLAUDE_PLUGIN_DATA}/cli`, so a warm run reads one small file with shell builtins. It still costs more than the `init` launcher (which is given absolute paths): in one run 44 ms against 26 ms p50, both on a loaded machine.
- **The MCP server is `jevmem mcp`, no wrapper.** The checklist holds MCP servers started through a shell for a reviewer. Without `jevmem` on the PATH Claude Code runs with, the server fails to start; the README says so, and the fix is `npm install -g jevmem`.
- **The key is a sensitive `userConfig` option** (manifest reference, "User configuration"): Claude Code keeps it in the system's secure credential store and exports it to hooks as `CLAUDE_PLUGIN_OPTION_TYPESAFE_API_KEY`; the MCP server gets it through `${user_config.typesafe_api_key}` in its `env`. jevmem copies it into `TYPESAFE_API_KEY` for that process only when it is non-empty and substituted, so an empty option falls back to `TYPESAFE_API_KEY`, then `~/.jevmem/env`.
- **`hooks/jevmem-hook.sh` at the repository root stays.** Projects set up with `jevmem init` have its absolute path in `.claude/settings.local.json`; moving it would break them until they re-run `init`.
- **Async Stop hooks read "cancelled" in `claude -p`.** With `--include-hook-events`, Claude Code reports every async Stop hook in a `-p` session as exit 1, outcome "cancelled", including one that only runs `true` (measured). The `nocli` e2e scenario therefore checks that hook's output, not its status.
  Measured again on Claude Code 2.1.284 (2026-09-29, `scripts/diag-stop-cancelled.sh`, [results](results/stop-cancelled-2026-09-29.json)): it is a race when `claude -p` exits, not jevmem's exit code. An async Stop hook that only runs `true` read "cancelled" in 4 of 6 runs; the directory's 0.5.7 plugin in 1 of 6 and `main`'s in 4 of 6, and in all 12 runs their Stop hook's CLI ran (it logged the turn). A Stop hook that is not async read "success" in 6 of 6. In an interactive session none of this shows: the spinner reads "running Stop hook" for about a second, then the turn is done, with no "cancelled" on screen or in the transcript. Nothing to fix in jevmem, so no release changes it; docs/hooks.md says what a `-p` user sees.

## v0.5.1: opt-in per project

- **Why.** In v0.5.0 the plugin, installed at user scope (the default), ran in every project Claude Code opened: prompts from work, private and client repositories went to TypeSafe's API, and `JEVMEM.md` and `.jevmem/` appeared in all of them. That contradicted the README and SECURITY.md, which describe jevmem as a per-project tool. v0.5.0 was not published, so the fix is in before anyone could install it.
- **The switch is `jevmem.config.json`.** A project has opted in when it contains that file, which `jevmem enable` and `jevmem init` write and which is committed with `JEVMEM.md`. One `-f` test, the cheapest check there is, and a file a reviewer sees in the repository. A clone of an enabled repository is enabled for a teammate who also has jevmem, which is the point of a committed memory file; a personal opt-out is `jevmem disable`.
- **Where the check runs.** First thing in `hooks/jevmem-hook.sh`, before Node is located, so a dormant hook costs one `sh` process and reads nothing but its stdin; again in `src/cli.ts` before the CLI bundle loads (for the plain `node … hook` command `init` registers for `UserPromptSubmit`); again in `cli-main` against the payload's `cwd` when `CLAUDE_PROJECT_DIR` is unset; and on every MCP tool call, so `enable` takes effect without restarting the server. The launcher's Node-path cache is written only in enabled projects, so a dormant project leaves no file anywhere, which `test/dormant.test.ts` checks by snapshotting the project, home, plugin-data and temp directories around real hook and MCP processes.
- **One rule for every hook, not only the plugin's.** `init` has always written `jevmem.config.json`, so existing projects are unaffected, and `jevmem disable` can then mean "off" for init hooks as well. The `{ "enabled": false }` setting from v0.5.0 still works but is no longer documented; `disable` replaces it.
- **`disable` sets the config aside, not away.** It moves `jevmem.config.json` to `.jevmem/jevmem.config.json.disabled`, so `enable` brings back thresholds `jevmem fit` wrote. `JEVMEM.md` is not touched.
- **The Stop launcher ignores SIGTERM first thing (0.5.2).** In 0.5.0 and 0.5.1 `trap '' TERM` sat inside the `--detach` block, after option parsing (and, in 0.5.1, after the opt-in check), which widened the window in which a session-end SIGTERM could kill the launcher before it handed the turn off; a loaded test run hit it. The trap is now the launcher's first statement. A signal that arrives before the shell has executed any line at all still cannot be caught by a script; in the `claude -p` probe the signal arrived after the hook's first lines had run.
- **`npx jevmem enable` in the README.** The plugin cannot put a command in the user's shell (a plugin's `bin/` only reaches Claude's Bash tool, and it blocks claude.ai/Cowork installs), so plugin-only users run it through `npx`; `jevmem enable` is the same command for npm users.

## v0.5.0: memory poisoning

- **Provenance is a separate file, not `decisions.jsonl`.** The brief said a line is verified when its id is in this machine's `decisions.jsonl`. Two things made that too weak: `decisions.jsonl` is trimmed to its last 500 records once it passes 1,000, so old lines would silently lose their status; and an id is public (it is in `JEVMEM.md`), so a pull request could edit the *text* of an existing line and keep its id. `.jevmem/provenance.jsonl` records the id and a hash of the exact text for every line jevmem writes (hook, `watch`, MCP `add_memory`, `import --apply`), is never trimmed, and a line is verified only when both match. Lines written before v0.5.0 have no record, so they count as unverified: each is gated once, then served from the cache.
- **Verified lines skip the gate; everything else pays one noul, once.** Verified lines already passed decide's injection check when they were saved. Unverified lines get a gate noul in the same recall call, and the verdict is cached by text hash (a line's verdict does not depend on the query), so a fresh clone pays about 257 input tokens per line on its first prompt and nothing after. `jevmem add` and `jevmem missed` lines are unverified on purpose: they were never gated.
- **Hidden text is refused in code.** Invisible characters, bidi controls, Unicode tag characters and inline HTML comments hide text from a reviewer reading the rendered file or a diff. No legitimate one-line memory needs them, so no Jev call is spent on them.
- **Fail closed.** If the recall call fails nothing is injected (as before); MCP `list_memory` without a key withholds unverified lines that were never checked.
- **The wording was tuned once, on a dev set.** `eval/memory-injection-dev.jsonl` (16 lines) was used for one pass: the first wording let a "use this registry mirror and make it the global registry" line through at 0.47, so "change machine, credential or security settings" was named and the criteria shortened. The 44-line eval set was then written, committed (`e9f4111`), and run twice without further changes. Its two misses (a signing key emailed "for approval", a registry swap tucked into a version rule) are reported, not tuned away.
- **Same threshold as the decide gate.** `injectionMax` (0.5) gates both a turn's injection family and a served line. One knob means `jevmem fit` and users tune one notion of "reads as instructions to an AI". In the eval, planted lines scored 0.38–0.97 and legitimate rules at most 0.38.

## v0.4.2: why `auto` lost contradictions, found on a dev set

- **Method.** The held-out set is the final exam, so this work used a new dev set (`eval/contradictions-dev.jsonl`: 43 cases, 27 reversals across explicit, implicit, different-vocabulary, partial, constraint/preference and similar-pair shapes, and 16 same-topic near-misses), committed before any run and tested to share no text with the prompts or the other eval sets. `scripts/diag-contradictions.mjs` records every tier's contradiction noul, family score, `touches_memory_id` distribution, injection nouls and final reason. The held-out set was run once, after the fix.
- **Before:** `fast` found 26/27, `auto` 20/27, `full` 19/27; no mode picked a wrong id or superseded a near-miss (`results/contradictions-dev-before.json`).
- **Where `auto` lost them.** Not in detection: tier 2's `reverses_or_replaces_a_listed_memory` fired at 0.88–0.98 and `touches_memory_id` picked the right id every time. They were lost at tier 2's *save* gate. The borderline rule escalated every turn with `contradicts_existing_memory ≥ 0.5`, so every reversal went to tier 2, and tier 2 then skipped it: its atomic kind nouls score a terse reversal ("Money columns become Decimal fields with four places.") as no content, and two injection nouls read changing a project rule ("I've changed my mind…", "the budget is relaxed…") as changing the AI's rules. A skipped reversal leaves the old line live next to nothing, so tools keep following the old decision.
- **Fix.** (1) A likely contradiction is no longer an escalation reason by default (`tiers.borderline.contradictionMin: 1.01`; tier 1 already detects and names them). (2) In the policy, a reversal of a listed memory (contradiction family ≥ `contradictionMin` *and* a named id) satisfies the content gate: a message that replaces a live memory is memory-worthy by definition. The kind, importance, chit-chat and injection gates still apply. (3) The "no" side of `tells_an_ai_to_ignore_or_replace_instructions` and `asks_the_ai_to_store_or_alter_memory_or_rules` now names changing or relaxing an earlier project decision or rule; the regression set's injection turns stayed refused in every mode.
- **No dedicated supersede call.** A separate "which memory does this replace?" `choice` was the fallback plan. The dev set gave no reason for it: wrong ids 0 and false supersedes 0 in every mode, before and after. It would only add a round trip to every saving turn.
- **After (two runs):** `auto` 25/27 both times, 0 wrong ids, 0 false supersedes, p50 311–323 ms on saving turns (`results/contradictions-dev-after-run*.json`). The two misses are partial reversals ("stays on the server, except aim-assist…", "may restart each fiscal year, as long as…") where the contradiction signal itself is weak; they are not tuned further.

## v0.3.3: the user message is the state

- **What went wrong in the first real desktop session.** With the hooks finally running, four of five saved lines were the assistant's words: a menu of options, two "Recorded. …" summaries, and a note about the hook output. `decide` judged a merged "USER … ASSISTANT …" string, so a chit-chat "thanks, looks good" turn scored as a decision because the *assistant* restated one, and the fallback writer then picked the assistant's sentence by cue words. The desktop assistant also runs Claude Code's own auto-memory, so its replies are full of "memory is set" prose, which made it worse.
- **Rule: the user message is the memory.** A statement from the user is sent alone. The assistant reply is sent, under its own key, only when the user asked a question (`looksLikeQuestion`: a `?`, or an opening like why/how/what/explain/investigate), or when there is no user text at all. When it is sent, a `content_source` choice says where the content lives and the policy allows only `bug` and `architecture` from `assistant_reply`; a `meta` family skips replies that are menus, self-summaries, or commentary about memory, hooks, or tooling. The writer gets the source text, never the blob.
- **Bug reports count as questions.** "The cache returns stale prices after logout" is a statement, but its memory-worthy content (the root cause) is in the reply. Without the reply, tier 2's bug family sees only "describes a failure" and scores 0.43. The heuristic therefore also fires on bug-report vocabulary (fails, broken, crash, error, flaky, stale, 500, `SomethingError`…), which only ever adds the reply to the state; the meta and source gates still decide what may be saved from it.
- **Why a code-side question heuristic rather than another noul.** Whether to include the assistant reply has to be decided before the call, and Jev accuracy drops with unrelated context, so the cheap heuristic keeps assistant prose out of the state on the ~80% of turns where the user made a statement. Its false negatives (a question phrased as a statement, "Investigate…" is covered) only mean the assistant's answer is not considered, which is the safe direction.
- **Context matters for reversals.** "Actually, we're submitting to the Chrome Web Store this week" is skipped as news with an empty memory list (importance 1.5, kind none) and saved as a superseding decision when the sideload decision is listed, in both tiers. The eval set therefore lets a turn carry its own `existing` memories, and the three real turns that followed the sideload decision have it.
- **No Stop hook on a max-turns abort.** With `--max-turns 3` Claude spent its budget reading the scratch repo and writing its own auto-memory, the turn ended with "Reached max turns", and no Stop hook fired (no `decide` entry). That is Claude Code behaviour, not jevmem's, and it means a hard-capped session can silently lose memories; the harness uses 15 and the README does not recommend low caps.
- **Harness over simulation.** `scripts/e2e.sh` drives a real `claude -p … --continue` session under `env -i` with a bare PATH, because the two bugs that mattered (PATH, assistant prose) were invisible to simulated stdin and to one-shot turns. It needs a logged-in standalone CLI; the desktop app authenticates its bundled binary through a host refresh channel that a child process does not get.

## v0.3.2: why the desktop-app hooks never fired

- **Reproduced, not guessed.** `launchctl getenv PATH` on the user's Mac is empty, so GUI apps run hooks with `/usr/bin:/bin:/usr/sbin:/sbin`; node lives under nvm. Running the real `claude` CLI with `env -i PATH=/usr/bin:/bin:/usr/sbin:/sbin` (no shell vars) in a scratch project reproduced the failure and, after the fix, produced a `JEVMEM.md` line from the Stop hook. The user's own test project (`~/Projects/linkguard`) had the PATH-dependent command `jevmem hook` and a log with no `decide` entries, which is exactly that failure.
- **Absolute paths only.** `init` writes `"<process.execPath>" "<realpath of cli.js>" hook`. It is uglier than `jevmem hook` but it works from any launcher. Re-running `init` repairs an older command in place so an upgrade is one command.
- **Key fallbacks read only named variables.** (Superseded in v0.5.4: shell profiles are no longer read.) Parsing the user's shell profiles is a compromise: it means "install, export the key like the README says, done" keeps working from the desktop app. The parser only extracts `TYPESAFE_API_KEY`, `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, the base URLs, and `JEVMEM_WRITER*`; it does not evaluate the profile and skips values that need shell expansion. A project `.jevmem/.env` (gitignored by `.jevmem/.gitignore`) or `~/.jevmem/env` is checked first for people who would rather not have profiles read.
- **Silent no-ops were the real bug.** Every early return in the hook path now leaves a `hook` line in `log.jsonl`; the debug log is opt-in because it stores prompt text.
- **`stop_hook_active` needs no special path.** Jevmem does not return a `decision: "block"`, so it does not cause a continuation loop; if another hook does, the extra stop is deduplicated by the turn hash.
- **"No tools, one sentence" is not an injection.** The real session's second turn was skipped because the injection family reached 0.54: a must/never rule plus "Acknowledge in one sentence, no tools" looked, to the `asks_the_ai_to_store_or_alter_memory_or_rules` and `tells_an_ai_to_ignore_or_replace_instructions` nouls, like an order to the AI. Users say this constantly in Claude Code, so every injection noul now lists it as a negative example and the eval set carries two such turns. The 40-turn set had none, which is a gap in the set, not a Jev regression.
- **One label left ambiguous on purpose.** The new eval turn "Decision: we must support Node 20 and 22; never bump engines above that." is labelled `constraint`; tier 1 answers `decision` (the message says so) and tier 2 answers `constraint`. Save/skip is right in every mode; the kind disagreement is reported as a miss rather than relabelled to match the output.
- **Payload compatibility is version-dependent.** CLI 2.0.30 sends `prompt` and no `last_assistant_message`; the current docs describe `user_prompt` and `last_assistant_message`. Both shapes are handled, and the transcript remains the source of the user text on every version.

## v0.3.1: two-tier decide

- **The literal borderline rule escalated 80% of turns.** With "any kind noul in [0.3, 0.7]" and "importance confidence < 0.6", 32 of 40 eval turns escalated (reason histogram: `contains_decision` 17, `contains_constraint` 12, `contains_architecture_fact` 11, importance 10, `contains_bug_finding` 3, preference 4, contradiction 1), and `auto` cost more than `full`. The cause is that a real decision turn also reads 0.4–0.6 on a neighbouring kind (constraint, architecture); tier 1 was right on 39 of those 40 turns regardless. The shipped rule keeps every condition from the brief but (a) applies the band to the strongest kind noul by default (`kindNoulScope: "max"`, with `"any"` still available), (b) adds `kind` choice confidence < 0.6 as a condition, (c) lowers the importance-confidence floor to 0.5 (its p25 across the set is 0.56), and (d) never escalates when tier 1 already scored injection > 0.7 or chit-chat ≥ 0.9, because tier 2 can only confirm a skip. Result: 15% escalation (6 of 40: the contradiction, three low-kind-confidence turns, two low-importance-confidence turns) at the same 97.5%.
- **Tier 2 keeps 1+1 examples.** Cutting tier 2 from two examples per side to one held 97.5% on three consecutive runs and dropped ~800 tokens per tier-2 call, so it stays at 1+1 (`tiers.tier2ExamplesPerSide: 1`; set 2 to restore).
- **Tier 1 is 2,318 tokens, not ≤ 2,000.** The twelve questions serialize to about 1,700 tokens after trimming every `what` to a clause and dropping `not_for` from the compact kind criteria; the remaining ~600 are the state (message, two previous turns, the memory list) and JSON framing, which no wording change removes. Trimming the compact importance rubric to summary + signals only lost a todo turn (95%), so `what` stays on the importance levels and "work agreed for later" is the first Useful signal.
- **Cost target missed, and why.** v0.2.0's twelve questions used plain-string criteria at 1,897 tokens. Adding one positive and one negative example to each noul is what the brief asked for and is worth ~400 tokens; that alone is 1.22× v0.2.0. With 15% escalation to a 5,463-token tier 2, `auto` averages 3,138 tokens, 1.65×. Getting to 1.3× would need escalation under 5% or a cheaper tier 2, neither of which we could justify on a 40-turn set where the escalated turns are exactly the ones (contradiction, low confidence) tier 2 exists for. `fast` mode is the 1.2× option for anyone who wants it.
- **Tier 1 uses the same policy shape as tier 2.** Each broad noul is its family's score, so `content = max kind noul`, and `evaluatePolicy` is shared. The only difference is that tier-1 finals read `tiers.tier1Thresholds` (fitted from tier-1 labels) over `thresholds`. That keeps `why` and `fit` symmetric across tiers.
- **Cache keys carry the tier** so a tier-1 and tier-2 call on the same state do not collide, and the log carries it so `stats` can compute the escalation rate as tier-2 decide calls over tier-1 decide calls.

## v0.3.0: Jev at its maximum

- **Decomposition tied, and we kept it anyway.** On the 40-turn hand-labelled transcript (`eval/transcript.jsonl`: 8 decisions, 5 constraints, 4 preferences, 5 bugs, 4 architecture facts, 4 todos, 4 chit-chat, 3 questions, 3 injection attempts), the v0.2.0 set of 9 broad nouls scored 97.5% and the v0.3.0 set of 30 atomic nouls scored 92.5% with the first hand weights and 97.5% after one tuning pass, on two consecutive runs. Both sets miss the same turn ("Can you explain how the cache layer works?" → the assistant's reply is a genuine architecture fact, which both classify as `architecture`; the label says skip because it is derivable from the code). The brief said to keep whichever scored higher; they tie, so the tie-breaker is what the atomic set enables: `why` can show which specific signal fired, and `fit` has 30 features to refit instead of 9. The cost is 3.3× the tokens per `decide` ($0.00026 vs $0.00008); latency is unchanged because Jev runs the questions in parallel. A 40-turn set is small (one turn is 2.5 points) and Jev's answers vary slightly between runs, so the honest claim is "no worse", not "better".
- **What the tuning pass changed.** The first hand weights gave every noul 2.0 with bias −3, which needs two strong nouls per family. Live answers showed each family has one "core" noul that fires alone (a constraint with must/never fires `states_a_rule_with_must_never_or_always` at 0.98 while the numeric-limit and consequence nouls stay near 0). Core nouls now carry 2.5–3.5, secondaries 1.0–2.0, bias −2.5. The `importance` rubric also gained "work agreed for later (a todo)" under Useful because a bare `TODO:` line was scored Minor.
- **`content` gates on the max kind family, `kind` still comes from the choice.** Jev is good at choice; the atomic nouls are better at "is there anything here at all". Requiring both means a fitted model cannot save a turn the choice called `none`; that is deliberate, and `missed` labels exist to catch it.
- **`fit` refits only what labels can teach.** Kind families are fitted against `label.kind`; `chit_chat` against "not saved and kind none"; `injection` and `contradiction` keep their defaults because the labels carry no injection or contradiction ground truth. Thresholds are grid-searched for F1 of `save`. Weights are pulled toward the hand-set start (small L2) so 40 labels cannot flip a family upside down.
- **Cache keys include the model.** A `jev-latest` upgrade changes answers; keying on `(model, state, questions)` means old entries simply stop matching. The daemon prewarm is not cached (its point is the network round trip).
- **Zero data retention is a passthrough flag.** The TypeSafe SDK forwards extra request fields; `zeroDataRetention: true` is what Vercel AI Gateway honours. It is only added when configured or when the base URL is a gateway, because an unknown field on the direct endpoint could be rejected.
- **Cursor is not tailed.** Cursor stores chats in `state.vscdb` (SQLite) under `~/Library/Application Support/Cursor/User/workspaceStorage/<hash>/`. Reading it would need a native SQLite dependency and would touch data outside the project and outside a plain log directory, so Cursor relies on the MCP path with an always-on rule. Codex writes `~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl` with `session_meta.cwd` and `phase: "final_answer"` assistant messages, which is exactly what a tailer needs, so `watch` supports Codex only.
- **`init --tool codex` edits `~/.codex/config.toml` only when it already exists and lacks `[mcp_servers.jevmem]`**, by appending. It does not rewrite the file; from v0.3.6 it prints the path, a backup path and the exact lines first, and keeps the backup.

## Warm daemon

- **Why a daemon and not a faster process.** The CLI itself starts in ~70 ms; the missing ~400 ms per cold hook call was TLS and connection setup to `api.typesafe.ai` in a brand-new process. Only a long-lived process can amortise that. The daemon is one `net.Server` on a Unix socket in `.jevmem/` (named pipe on Windows), holding one `TypeSafeClient`, and it runs the exact same `runHook` code path.
- **The hook does not wait on the daemon.** It tries to connect for 250 ms; on failure it does the work inline and spawns the daemon detached for the next turn. A crashed or outdated daemon costs one cold turn, never a broken one.
- **Idle exit, not a service.** No launchd/systemd, no global process: one daemon per project, it exits after 30 idle minutes, and `.jevmem/daemon.json` records the pid so `jevmem daemon status/stop` can find it. A pre-warm call of one tiny noul (~300 tokens, about a thousandth of a cent) opens the connection so even the first real turn after start is warm.
- **Scrub at the source, not only at the boundary.** The reviewer could not find scrubbing in `decide.ts` because it lived only in the client wrapper. It now happens in both places; the test suite (which mocks the client) can therefore prove it.

## Repo / tooling

- **Single package, not a workspace.** The brief said monorepo; one package with a CLI, hook, MCP server, and library entry is simpler to install (`npx jevmem`) and there is nothing yet that would justify a second package. The layout (`src/`, `test/`, tsup, vitest, eslint) is ready to become `packages/jevmem` if a second package appears.
- **ESM only, Node 20+.** Matches `@typesafe-ai/sdk` and the MCP SDK.
- **`pnpm-workspace.yaml` exists only to allow esbuild's postinstall** (pnpm 11 `allowBuilds`). It declares no packages.
- **zod v4** is used for MCP tool schemas (supported by `@modelcontextprotocol/sdk` ≥ 1.23).

## Lessons from the first live run

- **Jev reads literally, so the injection guard must name the attack, not the audience.** "Instructions aimed at an AI assistant" is true of every prompt in a coding session. The question now describes overriding rules or planting memory, and the criteria carry both true and false examples ("Switch the primary store to Postgres 16" is listed as false). Structured criteria with `what` + `examples` fixed it in one iteration.
- **Fallback extraction is kind-aware.** Questions are skipped, cue words per kind are rewarded, and for `bug`/`architecture` the assistant's sentence wins. The LLM writer makes this moot, but the no-key path should still produce a usable line.

# Claude Code hooks, and Cursor's

How `jevmem init` registers the hooks, where the hook finds your key, the warm daemon, what Claude Code actually sends, and, since 0.7.4, [Cursor's hooks](#cursor-hooks-074).

## The Claude Code plugin

The plugin lives in [`plugin/`](../plugin) and contains no jevmem code: a manifest, the hook configuration, one short POSIX shell launcher and a README. It runs the `jevmem` CLI you install from npm, so the install is:

```bash
npm install -g jevmem
claude plugin marketplace add Avinash-jetwani/jevmem
claude plugin install jevmem@jevmem
cd your-project && jevmem enable
```

Or add it in the Claude app from the Claude plugin directory, where Claude Code loads it as `jevmem@synced`: the steps are in [install.md](install.md#from-the-claude-plugin-directory).

**What it runs.** The hooks run `"${CLAUDE_PLUGIN_ROOT}/hooks/jevmem-hook.sh"` (quoted, as in Claude Code's plugin docs and as the plugin directory's checklist asks for a plugin in a subfolder): `UserPromptSubmit` synchronously, `Stop` with `"async": true` and `--detach`. Since 0.6.0, a third hook runs it for the guard: `PreToolUse` on Bash, Edit and Write, with `--guard`, which makes the launcher run only a CLI that has the guard ([Guardrails](guardrails.md)). Since 0.7.1 a fourth, `SessionStart`, runs it with the plain command, for the always-on lines ([below](#what-init-sets-up)). The launcher (1) ignores SIGTERM for `--detach`, (2) exits at once in a project without `jevmem.config.json`, (3) finds the `jevmem` CLI with `command -v jevmem`, else at the path it cached in `${CLAUDE_PLUGIN_DATA}/cli` the last time it found one, else in `/opt/homebrew/bin`, `/usr/local/bin`, `~/.local/bin` and `~/.volta/bin`, in that order, else in the newest Node version under `~/.nvm/versions/node` that has it (it runs no package manager to find it), (4) finds Node 20+ to run it with, (5) prints one warning line to stderr when the CLI is older than the plugin, and (6) runs `jevmem hook --plugin`, for `Stop` by saving the hook JSON to a temp file and starting the CLI in its own process group. Steps 4 and 5 are cached in the same file per CLI file and plugin version. The directory list covers the desktop app, which can run hooks with a PATH that lacks `jevmem`. It downloads nothing. As a process, the plugin's Stop launcher took 14 ms p50 against 12 ms for the `init` launcher in the same run (v0.5.6), and 15 ms on a bare PATH with the CLI in `~/.local/bin`, read from the cache after the first run; the turn's decision was recorded 260–272 ms after it started ([Cost math](cost.md#cost-math)).

**When the CLI is missing** (since v0.5.6). In a project without `jevmem.config.json` the launcher still exits before looking for anything, and prints nothing. In an enabled project where it finds no `jevmem` CLI, memory is off, and the `UserPromptSubmit` hook returns one `systemMessage`, which Claude Code shows you: "jevmem: CLI not found, so memory is off in this project. See the jevmem README to set it up", with a link to the README. It is shown once per session (the session ids already told are kept in `${CLAUDE_PLUGIN_DATA}/notified`); the async `Stop` hook stays silent, and both exit 0. Since 0.7.3 it is not shown in a cloud or Cowork session (where the launcher is, by the two variables under the one-time message below): every chat there is a new session, and the command cannot be put in place from the chat. A CLI with no Node 20+ to run it gets the same treatment, with "Node.js 20 or newer not found". Until v0.5.5 both cases were silent. The MCP server is the plain command `jevmem mcp`: without `jevmem` on the PATH Claude Code runs with, it fails to start (`/mcp` shows it) until you `npm install -g jevmem`.

**The one-time setup message** (since 0.7.2). Someone who adds the plugin in the Claude app still has steps to do by hand before anything happens, and until 0.7.1 nothing said so: in a project that is not turned on the launcher printed nothing. Now the `SessionStart` hook's entry carries `--start`, and the launcher, while `~/.jevmem/setup-notice` does not exist, works out what is missing with two shell tests (no CLI is run, nothing is sent, and no key is read: the launcher looks for the `jevmem` command, its usual search, and for this project's `jevmem.config.json`). It says the missing step in one line, with `jevmem setup` as the one command, and writes the marker, so the message shows once per computer; when the command is there and the project is on it writes the marker and says nothing, since the CLI then runs and its own notice names the key step at the first prompt when none is saved. The two texts, word for word except that the first spells out the README's web address, which this page does not (the plugin directory's scanner reads the names of package managers and the word that goes with them as an install step, so the first text points to the [README](../README.md#install) instead of quoting the line): "jevmem: the plugin is added, but the jevmem command it runs is not on this computer yet, so it does nothing. To finish: get the jevmem command (one line, in the README: <the README's web address>), then run jevmem setup in a project folder (it asks for your TypeSafe key and turns jevmem on there). Shown once." "jevmem: the jevmem command is in place, but jevmem is not turned on in this project, so nothing is saved or sent from here. To turn it on here: run jevmem setup in this folder (it asks for your TypeSafe key if none is saved). Shown once." How it reaches you: the hook returns it as a `systemMessage`, which Claude Code's terminal prints at startup as `SessionStart:startup says: …` (seen on 2.1.300), and, outside a terminal, also as `additionalContext` that asks Claude to pass it on at the start of its first reply, because the Claude desktop app's Code tab does not draw a hook's systemMessage (2.1.295: the hook ran, Claude Code recorded the message, nothing was shown). **Where it shows** (since 0.7.3): only on your own computer, where the marker stays. The launcher reads two variables Claude Code gives its hooks: `CLAUDE_CODE_REMOTE`, which Claude Code's docs set to `true` in a cloud session and never locally, and `CLAUDE_CODE_ENTRYPOINT`, which Claude Code sets in every session but does not document (the values below are Claude Code's own, read from its code and from sessions on 2.1.300). A terminal (`cli`) gets the message alone; the desktop app's Code tab (`claude-desktop`), the VS Code extension (`claude-vscode`) and the desktop app's SSH sessions (`ssh-remote`) get it with the context for Claude. A cloud session (`CLAUDE_CODE_REMOTE=true`, or an entrypoint that starts with `remote`: a claude.ai chat that runs in a cloud workspace has `remote_cowork`), Cowork on the desktop (`local-agent`, or `CLAUDE_CODE_IS_COWORK`), Claude Tag (Slack, Teams) and GitHub Actions get no message, no marker and no `~/.jevmem` folder: such a chat runs in a new workspace with a new home folder, so 0.7.2's "once" was every chat, and nobody can put the `jevmem` command there from the chat. Any other entrypoint, or none, gets no message and no marker either: a `claude -p` run is `sdk-cli` (measured on 2.1.300), so a script sees nothing, and a later terminal or app session on the same computer still gets the message once. In a cloud or Cowork session the plugin's hooks still run (the plugin is synced from your claude.ai account), find no `jevmem` command and stay silent: memory is off there unless the environment installs the CLI and gives it a key ([limits](limits.md)). The marker, `~/.jevmem/setup-notice`, is one line (`shown <step> <time>` or `done <time>`), readable only by you; `jevmem setup` writes it when it finishes, and creating it by hand (`mkdir -p ~/.jevmem && touch ~/.jevmem/setup-notice`) is the opt-out, which needs no CLI. After the marker exists a session start costs the launcher one file test more than before. Nothing is written inside the project, and the other hooks in a project that is not on stay as silent as before (tested: the `nocli`, `nokey`, `dormant`, `setup` and, since 0.7.3, `remote` e2e scenarios, and the unit tests of each state and each entrypoint).

**Your key.** Run `jevmem setup`, which asks for it while finishing the setup, or `jevmem key`, and paste your TypeSafe API key; either saves it in `~/.jevmem/env`, readable only by you. That works for every install, including the plugin added from the Claude plugin directory, which Claude Code loads as `jevmem@synced` and which has no Configure options. A plugin installed from a marketplace can instead take the key with `/plugin configure jevmem` in Claude Code; the `claude plugin install` shell command doesn't ask for it. That setting is the `typesafe_api_key` [user configuration](https://code.claude.com/docs/en/plugins/manifest-reference#user-configuration) option, marked sensitive, so Claude Code keeps it in your system's secure credential store rather than `settings.json`. Claude Code passes it to the hooks as `CLAUDE_PLUGIN_OPTION_TYPESAFE_API_KEY` and to the MCP server through `${user_config.typesafe_api_key}`. It is used before `TYPESAFE_API_KEY` and `~/.jevmem/env`, which remain the fallbacks when you leave the option empty. jevmem never writes the key to a file or a log.

**The plugin does nothing until you run `jevmem enable` in a project.** Installed for the user (the default), it is loaded in every project you open, but in a project without `jevmem.config.json` its hooks and MCP server make no network calls, create no files and print nothing, and the MCP tools answer only "jevmem isn't enabled in this project: run `jevmem enable`". `jevmem enable` creates `jevmem.config.json`, `JEVMEM.md` and `.jevmem/` and adds `.jevmem/` to `.gitignore`, like `init` without the hooks; `jevmem disable` sets the config aside (in `.jevmem/`, restored by the next `enable`) and leaves `JEVMEM.md` alone. A project that also has `jevmem init` hooks would run jevmem twice per event, so the plugin's hooks stand down there, log it once a day, and show a one-line warning once per session; `jevmem init --remove-hooks` removes the init hooks. On Windows the plugin needs Git for Windows' `sh` on PATH.

## What `init` sets up

`jevmem init` also opts the project in (it writes `jevmem.config.json`). If a project has both the plugin and `init` hooks, the plugin's hooks stand down (nothing runs twice) and say so once per session; `jevmem init --remove-hooks` removes the init hooks and keeps only the plugin.

`jevmem init` creates `JEVMEM.md`, `jevmem.config.json`, a gitignored `.jevmem/` folder, and registers the Claude Code hooks in `.claude/settings.local.json` (per-machine; `jevmem init` adds it to `.gitignore`, and creates a `.gitignore` in a git repository that has none). The file is per-machine because the registered command uses the absolute paths of `node` and the CLI (Claude Code runs hooks without your shell profile and, from the desktop app, with a bare PATH). If you upgrade or move Node, run `jevmem init` again and it repairs the command in place; a jevmem hook found in the shared `.claude/settings.json` is moved to the local file. Every command accepts `--help`.

With no `--tool`, `init` sets up whatever it finds **in the project** (`.claude/`, `.cursor/`, `AGENTS.md`), and Claude Code when it finds nothing. It never looks at your home directory, and it edits `~/.codex/config.toml` only when you pass `--tool codex` or `--tool all`.

| Hook | What it does | Budget |
|---|---|---|
| `Stop` (async) | Reads the turn that just finished, queues it and hands it to the daemon, which makes one Jev call (two on borderline turns: 6–14% of turns in the v0.4.2 evals, 2026-09-23) and writes one line if Jev says so (since 0.6.0, with one more call for a saved turn, to pick the line's sentences). | Returns in milliseconds; Jev 2 s per call, writer 8 s, in the daemon; exits 0 on any failure (tested by spawning the built CLI) |
| `UserPromptSubmit` | Makes one Jev call to pick the five memories most relevant to your prompt and injects them as context (since 0.6.0: the lines Jev judges relevant, at most five, [how](how-it-works.md#the-read-side-one-call-per-prompt-srcrecallts)). | Jev 1 s (`jev.recallTimeoutMs`; past it, or when the call fails, the lines sharing the most words with your prompt) |
| `PreToolUse` (the guard, since 0.6.0) | Checks each Bash, Edit and Write call against the project's saved `[constraint]` rules and, when Jev says it may break one, has Claude Code ask you, block it or tell Claude ([Guardrails](guardrails.md)). Most calls share nothing with a rule and make no request. | The hook entry's timeout is 3 s; its own budget `guard.budgetMs`, 2,000 ms; fails open, except that a rule matched on more than keywords is asked about when Jev does not answer in time |
| `SessionStart` (since 0.7.1) | Puts the project's always-on lines in front of Claude at the start of every session (startup, resume, clear, compact), read from `JEVMEM.md` alone: no Jev call and no key needed ([How it works](how-it-works.md#always-on-rules-071)). Since 0.7.2 the lines go through the poisoning gate's plan from the local files (verified, or a cached clean verdict), and the plugin's launcher says once per computer, on your own computer and not in a cloud or Cowork session (0.7.3), what is left of the setup while it is unfinished. | Milliseconds; the hook entry's timeout is 5 s |

**Always-on rules reach every session** (since 0.7.1). A line marked always-on (Jev marks a rule every change must follow when it saves it; `jevmem add --always` and `jevmem always <id>` mark by hand; `jevmem always --suggest` proposes marks for a file from before 0.7.1) goes into Claude's context at the start of every session through the `SessionStart` hook, under `<jevmem-rules>`, each with its id, at most `alwaysOn.maxLines` (40) in file order. When no session-start hook served a session (Claude Code cancelled it before the first prompt, which happened in 3 of 216 sessions of the release's design runs, or the hook is not registered), the `UserPromptSubmit` hook sends the same lines with the session's first prompt, marked `(id:…, always)`, and not again: the session-start hook records the sessions it served in `.jevmem/sessions-served.json` (the last 200 ids), which the prompt hook reads. Claude Code runs the hook again on resume, clear and compaction, and once a `SessionStart` hook is registered it starts each `claude -p --continue` turn as a resume with a new session id (Claude Code 2.1.296 and 2.1.299, measured 2026-10-14: the turn is appended to the first turn's transcript and the conversation goes on), so a scripted session gets the block again on each such turn. `jevmem init` registers the fourth hook; re-running it in a 0.7.0 project adds the hook and changes nothing else. `alwaysOn.mode` in `jevmem.config.json` is `always` (the marked lines), `constraints` (every live `[constraint]` line instead) or `off` ([configuration](configuration.md)). **Since 0.7.2 a marked line reaches Claude only when the poisoning gate lets it** ([SECURITY.md](../SECURITY.md#memory-poisoning)): at session start, with the first prompt and in `constraints` mode, a verified line (jevmem wrote it here, or you trusted it) or an unverified line whose cached gate verdict passed is served; a line the gate withheld is not, and a line with no verdict yet waits. Until 0.7.1 every live marked line was served from the file alone, so a line that arrived through a pull request with `always:1` in its comment reached every session. How a line gets its verdict: `jevmem always <id>` and `jevmem add --always` ask the gate once when they mark (one request with the line, as `jevmem trust` makes; a line it withholds is not marked, with the reason); the prompt hook gates the always-on lines still waiting ahead of the other unchecked lines, so a line from a pull request gets its verdict on the first prompt after it lands, and that prompt's fallback serves it when the call cleared it; `jevmem audit --security` gates every line now; `jevmem doctor`'s `always` line counts the lines served, waiting and withheld. The session-start hook still reads the file alone: no request, no key.

That's it. Keep working. `JEVMEM.md` fills itself, and it's a normal file: edit it, commit it, review it in PRs.

By default jevmem writes the line itself: the most relevant sentence of the turn, trimmed to 200 characters at a word boundary, not inside a URL (tested). Since 0.6.0, Jev picks the sentences: the one that states the memory, not a request or a hand-off to Claude, and the one that gives its reason, both kept when they fit in 200 characters. That is one more request, made only for a turn that is saved; when it fails, the writer picks one sentence by the words it looks for, as up to 0.5.10, and `jevmem doctor` lists it ([How it works](how-it-works.md#the-line-srcpickts-srcwritets)). An LLM writer (OpenAI or Anthropic) condenses the turn instead only when `jevmem.config.json` sets `"writer": "openai"` or `"anthropic"` ([configuration](configuration.md#the-one-line-writer)); an OpenAI or Anthropic key in your environment is not enough on its own. Without `TYPESAFE_API_KEY` the hooks no-op and say so in `.jevmem/log.jsonl`. Since 0.5.10 they also tell you, once per project, on your next prompt: what is missing, where jevmem looks, and the command that fixes it, `jevmem key`, for the plugin's hooks and `jevmem init`'s alike. It is shown again only if a key was found and later went missing. Also since 0.6.0: when jevmem saves its first line in a project, the next prompt shows "jevmem saved its first line to JEVMEM.md.", once, so you can tell jevmem's memory from Claude Code's own, which may also say it saved something. A project where jevmem saved lines before is not told.

**Where the hook finds your key.** Claude Code hooks (and MCP servers started by Cursor, Codex, or Claude Desktop) do not get your shell's variables, and jevmem does not read shell profiles. It looks for `TYPESAFE_API_KEY` (and the writer keys) in this order: the plugin's key setting, the process environment, `<project>/.jevmem/.env`, then `~/.jevmem/env`. The last two are jevmem's own files, which you create. `jevmem key` (since 0.5.10) puts `TYPESAFE_API_KEY=...` in `~/.jevmem/env` for you, asking for the key without showing it and asking before it replaces a key already there. Since 0.5.8 the MCP server reads the two files too, on each call, so a key saved while it runs is used without a restart (0.5.7 and earlier read only its environment and the plugin setting). Since 0.5.10 the hooks' warm daemon also switches to a key saved or replaced while it runs, from the next prompt. `jevmem doctor` says which one it found, without printing the key.

**When Jev is down.** A Stop turn is first written, scrubbed, to `.jevmem/queue.jsonl`, and turns are evaluated from there oldest first. If Jev times out or answers 408, 429 or 5xx (529 included), the turn stays at the head and is retried after 15 s, 30 s, 1 min, 2 min, 5 min, then every 10 min, on the next hook run or by the idle daemon (which stays up while turns are queued); newer turns wait behind it so a reversal is never decided before the decision it reverses. A turn already decided is not evaluated again (its hash is checked against `.jevmem/decisions.jsonl`; tested). Turns older than 24 hours, or beyond 200 in the queue, are dropped with a `dropped` line in `.jevmem/log.jsonl`. Other errors (a 400, a bad key) drop the turn with a log line as before. `jevmem stats` shows queued, retried, saved-from-queue, dropped and pending counts. Since 0.6.0, `jevmem stats` and `jevmem doctor` also list the last 7 days' failures from the log: each dropped turn with its reason (a hook that found no key included), each recall request that failed (that prompt got no project memory), and each guard check that failed or timed out.

**A turn is decided once, when it is over** (since 0.6.0). With a background subagent, which is how an interactive Claude Code session runs every subagent, the main agent stops while the subagent works, so Claude Code runs the `Stop` hooks in the middle of the turn; the subagent's report comes back later as a `<task-notification>`, and the turn goes on. The Stop hook reads the transcript into turns (a prompt you typed and everything the main agent wrote until your next one; a task notification is not a prompt) and decides nothing while a subagent the turn launched in the background has not reported back. It decides the whole turn once: at the Stop that ends it, when your next prompt closes it, or when its session has written nothing for 10 minutes (the session ended, or the subagent was stopped). Until then the turn waits, with its text so far, in `.jevmem/turns.json`, and `jevmem stats` counts it. A background shell command does not hold a turn. Up to 0.5.9, and on `main` before this, each of those Stops was decided on its own: the request with only "I've started a subagent…", then the notification as if it were your message. How this was measured: [Benchmark](benchmark.md#the-stop-hook-with-background-subagents).

**The Stop hook does not make you wait** (since v0.5.0). `init` registers it with `"async": true`, so Claude Code carries on without waiting for it, and on macOS and Linux its command is the package's POSIX launcher, `sh ".../hooks/jevmem-hook.sh" --node "<node>" --detach hook`. The launcher saves the hook JSON to a temp file, starts node in its own process group and exits: 13–15 ms p50 as a process (v0.5.0, 2026-09-25), against 355 ms for the v0.4.5 hook that waited for Jev through the warm daemon ([Cost math](cost.md#cost-math)). Node then queues the turn and hands it to the daemon, which decides and writes it; the decision was recorded 221–428 ms p50 after the hook started. The own process group matters: when a session ends, Claude Code sends SIGTERM and then SIGKILL to an async hook's process group, and with `claude -p` that happens as soon as the Stop hook starts. On macOS, which has no `setsid`, the launcher uses the shell's job control; bash then sometimes prints "child setpgid (…): Operation not permitted", when the shell and the new process both set the group and the second one fails. Node is in its own group either way: in 12,000 launches through `main`'s launchers (2026-09-27), with the hook's group killed as soon as the hook exited and a local stand-in for Jev deciding the turns, the message came 18 times and every turn was decided ([results](../results/setpgid-2026-09-27.json)). Since 0.6.0, the launchers send it to `/dev/null`; in 0.5.8 it can show on the `Stop` hook's stderr. The CLI's own errors go to `.jevmem/log.jsonl`. On Windows the Stop command is the plain node command, still async. With `claude -p --include-hook-events`, the `Stop` hook's event can read exit code 1, outcome "cancelled": when `-p` exits, Claude Code closes the async hooks still open, and a hook that only runs `true` reads the same. The launcher has already handed the turn on by then, and the turn is decided. An interactive session shows "running Stop hook" for about a second and nothing more ([results](../results/stop-cancelled-2026-09-29.json)). Re-running `jevmem init` upgrades a v0.4 project's Stop hook in place. `UserPromptSubmit` stays synchronous: its output is the context Claude reads.

The first hook call in a project starts a small **warm daemon** (`jevmem daemon status` to see it) that keeps the Jev client's connection open and evaluates the turn queue. It exits after 30 idle minutes (not while turns are queued) and is off with `JEVMEM_DAEMON=0`, in which case the detached hook process evaluates the queue itself. Through the warm daemon, `UserPromptSubmit` took 302–304 ms end to end including Node start-up, against 629–642 ms as a cold process (v0.5.0, 2026-09-25).

### Local files for the pane

Since 0.7.1 the `SessionStart` hook also writes `.jevmem/sessions-served.json`, the ids of the last 200 sessions it served (so the prompt hook knows when a session got no session-start context); it holds ids and nothing else.

Since 0.7.0 the hooks write two small files in `.jevmem/` (gitignored, and `.jevmem/.gitignore` holds `*`), one prompt or turn each, overwritten by the next, through a temporary file and a rename so a reader never sees half of one. The side pane ([docs/pane.md](pane.md), `jevmem-pane`, 0.7.5) reads them, and the guard log's `tool_use_id`, to show what each prompt got, what the guard decided and what each turn saved; nothing else reads them, and nothing in them is sent anywhere.

`.jevmem/last-recall.json`, written by the `UserPromptSubmit` hook after recall, whether or not the prompt got a line, and since 0.7.5 also in a project with no memory line yet (then `path` is `none`, `served` is empty and `lines` is 0, so the pane can say so instead of showing a stale file; `lines` is the count of live lines):

```json
{
  "ts": "2026-10-08T12:00:00.000Z",
  "session_id": "…",
  "prompt_hash": "16 hex characters: sha1 of the prompt",
  "path": "jev",
  "served": [{ "id": "ab12cd", "kind": "decision", "text": "…", "p": 0.98 }],
  "withheld": [{ "id": "k3x9ab", "reason": "reads as instructions aimed at an AI (gate 0.91 ≥ 0.5)" }],
  "gated": 1,
  "deferred": 0,
  "ms": 310,
  "lines": 12
}
```

`path` is `jev` or `word-match` (then each served line has `shared_words` instead of a meaningful `p`, and `error` says why Jev did not answer); `gated` is how many unverified lines the call checked, `deferred` how many it left for a later prompt. `served` is in the order the lines were injected.

`.jevmem/last-decision.json`, written when a turn's decision is made (by the hook or the daemon, so after the `Stop` hook returns: on 2026-10-17 it landed 520 to 799 ms after the turn ended, on 15 of 15 turns never before; [results](../results/pane-probe-2026-10-17.json)). Since 0.7.5 it carries `session_id` and `prompt_hash` (the hash the recall file has for the prompt), so the pane matches the decision to its prompt and its session and not only by time; and the `Stop` hook writes it at once when it decides nothing for the turn it was called for: `action` `deferred` for a turn whose background subagents are still running, `skipped` for an empty turn, each with the reason and `source` `stop-hook`, so the pane need not wait for a limit. A repeated `Stop` of a turn already captured writes nothing.

```json
{
  "ts": "2026-10-08T12:00:05.000Z",
  "hash": "the turn's hash, as .jevmem/decisions.jsonl has it",
  "action": "saved",
  "detail": "[decision] Use Postgres 16 for the main database id:ab12cd via fallback (…)",
  "kind": "decision",
  "line": "Use Postgres 16 for the main database",
  "id": "ab12cd",
  "superseded": null,
  "duplicate_of": null,
  "reason": "save kind=decision content=0.98 importance=important [tier 1]",
  "source": "user_message",
  "tier": 1,
  "ms": 290,
  "session_id": "…",
  "prompt_hash": "16 hex characters: sha1 of the prompt"
}
```

`action` is `saved`, `skipped` (then `kind`, `line` and `id` are null and `reason` says why; a duplicate has `duplicate_of`), `deferred` (0.7.5, above) or `error`. `jevmem why <hash>` has the whole decision behind it.

## Cursor hooks (0.7.4)

Cursor runs a project's `.cursor/hooks.json` hooks, in the app and in its `agent` CLI, with a JSON payload on stdin and the project root as the working directory ([Cursor's docs](https://cursor.com/docs/hooks), read 2026-10-16). `jevmem init --tool cursor` writes jevmem's entries into that file, beside `.cursor/mcp.json` and the rule, and copies a launcher into the project:

```json
{
  "version": 1,
  "hooks": {
    "sessionStart": [{ "command": "sh .cursor/hooks/jevmem-hook.sh sessionStart", "timeout": 5 }],
    "beforeSubmitPrompt": [{ "command": "sh .cursor/hooks/jevmem-hook.sh beforeSubmitPrompt", "timeout": 5 }],
    "afterAgentResponse": [{ "command": "sh .cursor/hooks/jevmem-hook.sh afterAgentResponse", "timeout": 5 }],
    "stop": [{ "command": "sh .cursor/hooks/jevmem-hook.sh stop", "timeout": 20 }],
    "sessionEnd": [{ "command": "sh .cursor/hooks/jevmem-hook.sh sessionEnd", "timeout": 20 }]
  }
}
```

**Both files can be committed.** Cursor's docs say project hooks are checked in, so the commands are relative and the launcher, `.cursor/hooks/jevmem-hook.sh` (POSIX sh, a copy of the package's `hooks/jevmem-cursor-hook.sh`), holds no path of one computer: it finds the `jevmem` command as the Claude Code plugin's launcher does (`command -v jevmem`, else the path it cached in the gitignored `.jevmem/cursor-launcher`, else `/opt/homebrew/bin`, `/usr/local/bin`, `~/.local/bin`, `~/.volta/bin`, else the newest nvm Node that has it), finds a Node 20+ to run it with, and runs `jevmem hook --cursor`. Cursor runs a project hook with its own resolved shell environment, not the environment of the process that started the agent (measured in the e2e: with the packed CLI first on the agent process's PATH, the launcher found the global `jevmem` on Cursor's PATH), so the launcher runs the `jevmem` Cursor's PATH has, and a jevmem before 0.7.4 found there exits 0 with nothing on `hook --cursor`; `jevmem doctor` names the CLI the launcher last ran and its version. The launcher also takes `--cli <path>` and `--node <path>` before the event name, an explicit CLI and Node that come before any search (the e2e harness uses them for the packed CLI; a committed file has no such path). A clone where jevmem is not installed, or a project without `jevmem.config.json`, gets a launcher that reads its input and exits 0 at once, answering `{"continue": true}` for `beforeSubmitPrompt` and nothing for the rest; nothing is written anywhere. Other hooks in the file are kept; running `init` again changes nothing, repairs a moved command or an older launcher, and `jevmem init --remove-hooks` takes jevmem's entries and the launcher out (a file left with nothing is deleted). A project set up with an earlier version needs `jevmem init --tool cursor` once more, which adds the two files and replaces the rule's text when it is unchanged; reload the window once.

**What each hook does.** Measured on Cursor 3.24.18 and the `agent` CLI (2026.08.11 to 2026.10.16) with a logging-only hook before any code (the payloads, with a note on how they were taken, are in [`test/fixtures/cursor/`](../test/fixtures/cursor/README.md)):

| Hook | Fires | What jevmem does | Budget |
|---|---|---|---|
| `beforeSubmitPrompt` | The app, when you send a prompt (the CLI does not fire it) | Writes the prompt and the turn's `generation_id` to `.jevmem/cursor/<conversation id>.json` and answers `{"continue": true}`, which it answers on any failure too: a hook answer Cursor cannot read could hold a prompt back | A file write; the entry's timeout is 5 s |
| `afterAgentResponse` | The app, once per turn, with the final message's text (a text block before a tool call was not reported in the probe) | Appends the text to that file; answers `{}` | The same |
| `stop` | The app, when the turn ends, with `status` `completed`, `aborted` or `error` and a `transcript_path` | `completed`: reads the turn **from the transcript** Cursor names, a JSONL of the whole conversation (one line per message; the person's text wrapped in `<timestamp>` and `<user_query>`, which are stripped; the assistant's text blocks joined, its `tool_use` blocks skipped; a `turn_ended` line when a turn finishes, and a resumed CLI chat's file keeps only the last one, so a turn is also closed by the next person's line; a line Cursor wrote itself after a background task, its follow-up, continues the turn), or, when there is no transcript, from the stash; then the same queue, decide and write as the Claude Code `Stop` hook, with the turn before it as context. `aborted` and `error`: nothing is decided, the stash is dropped. The launcher saves the payload and starts the CLI in its own process group, as the Claude Code Stop launcher does, because Cursor waits for a `stop` hook's answer (it may carry a follow-up prompt; jevmem never returns one) | Hands off in milliseconds; decide runs detached (601 ms p50 inline on the dev set, decide included) |
| `sessionEnd` | The app when a chat ends (`reason` `completed`, `aborted`, `error`, `window_close`, `user_close`); **the CLI at the end of every `agent -p` run**, which fires none of the three above | `completed`: the transcript's last finished turn, when it is not decided yet. This is how a headless CLI run is saved; in the app it adds nothing after `stop` | The same |
| `sessionStart` | Both, once per new chat | The project's always-on lines as `additional_context`, through the same gate as the Claude Code `SessionStart` hook (verified lines, or lines whose cached gate verdict passed), once per conversation | Milliseconds, no request, no key |

A turn is marked decided by conversation id and turn number (`.jevmem/turns.json`), so a `stop` fired twice, or `sessionEnd` after `stop`, decides nothing twice. Stashes older than a day are deleted by any later hook. Recall is not automatic in Cursor: `beforeSubmitPrompt` has no field for context, so the agent reads memory with `search_memory` over MCP when the rule tells it to; in the Cursor app that needs the project's MCP server turned on once (Customize → MCPs → jevmem → Configure → the source toggle for `.cursor/mcp.json`, then Reload; [the step](mcp.md#cursor)).

**Cursor also runs a project's Claude Code hooks.** With its third-party import on (Cursor's default), Cursor loads `.claude/settings.local.json` and `.claude/settings.json` hooks and runs them with its own payloads and event names (`beforeSubmitPrompt`, `stop`, `sessionStart`, `preToolUse`), which `jevmem hook` without `--cursor` does not act on: measured on 2026-10-16 with 0.7.3's four hook commands and every payload of the probe, each exited 0 with no output, no request and no file (`test/cursor-payloads.test.ts` keeps it so). A project with both runs jevmem once per event, through the Cursor entries.

**Measured.** Twenty real Cursor sessions, captured through the `agent` CLI in scratch copies of the eval projects before any Cursor code (`eval/cursor-dev-sessions.jsonl`, 10 sessions and 26 runs; `eval/cursor-heldout-sessions.jsonl`, 10 sessions and 24 runs in other projects, not read while building), each run's pair labelled from the CLI's own events, then replayed through the built `jevmem hook --cursor` with the real Jev (`scripts/eval-cursor.mjs`). On the held-out set, run once on the build: 21 of 24 turns paired whole; the three misses were one session where Cursor's CLI had submitted a follow-up of its own as a user line after a background task, which the reader took as a new turn. Fixed in the release, and the set run a second time: **24 of 24 turns paired whole** (the prompt without Cursor's wrappers, the whole reply as the CLI reported it, no tool output, the one interrupted run read as open and left alone), and decide, unchanged from Claude Code, right on save or skip for 21 of 24, with the kind for 20 of 24, every saved line carrying its labelled words (14 of 14), the one reversal superseded, precision 14 of 17, recall 14 of 14 ([results](../results/cursor-heldout-2026-10-16-v074-run2.json), [the first run](../results/cursor-heldout-2026-10-16-v074.json)). The three decide misses are two questions whose reply stated a fact, saved as architecture lines, and a "Run the tests" whose reply found the failing runner, saved as a bug: the behaviour 0.6.0 chose for a fact in the reply ([limits](limits.md)). The dev set on the same build: 26 of 26 paired whole, save or skip right 23 of 25 counted turns (one run is left out: its agent read this repository's labels), with the kind 21 of 25, 2 of 2 reversals ([results](../results/cursor-dev-2026-10-16-v074.json)). The Grok 4.7 Extra High model served every captured session; the CLI updated itself from 2026.10.14 to 2026.10.16 between the first and the other sessions.

## The jevmem plugin for Cursor (0.7.6)

Since 0.7.6 the same saving comes as a Cursor plugin, `cursor-plugin/` in this repository, listed in the repository's `.cursor-plugin/marketplace.json` as `jevmem`: the five hooks above, the MCP server and the rule, in every Cursor window at once, with no file written into a project. Like the Claude Code plugin it ships no jevmem code: one POSIX launcher, `hooks/jevmem-hook.sh` (the package's `hooks/jevmem-cursor-hook.sh`, copied; a test holds the two equal), runs the `jevmem` CLI from npm, which needs a TypeSafe key saved with `jevmem key`. Install it from the Cursor Marketplace once it is listed there, or now by copying the folder to `~/.cursor/plugins/local/jevmem` and reloading the window ([install](install.md#the-cursor-plugin-076)); then turn each project on with `jevmem setup` or `jevmem enable`.

**What Cursor does with a plugin, measured on 2026-10-18 with Cursor 3.25.9 and the `agent` CLI 2026.10.16** (a logging-only probe plugin before any code, as 0.7.4's probe; the app's own Hooks output channel; the CLI's stream):
- A plugin's hooks fire in the app and in the CLI (the CLI loads `~/.cursor/plugins/local/` on its own and fires `workspaceOpen`, `sessionStart` and `sessionEnd`, as it fires a project's). `${CURSOR_PLUGIN_ROOT}` is substituted into the hook's command before the shell runs it, and is an environment variable too (with `CLAUDE_PLUGIN_ROOT` the same). The working directory is not the project: the project root for a Cursor-format plugin's hook in the app, the plugin folder in the CLI and for a Claude-format plugin's hook in the app. So the launcher takes the project from `CURSOR_PROJECT_DIR`, which Cursor sets for every hook, and the entries' timeouts are the project entries' (Cursor's default for a plugin hook is 60 s).
- A plugin's MCP server starts with no per-project toggle: the app starts one per window the moment the plugin loads, from the home folder as working directory, with `${workspaceFolder}` in `mcp.json` expanded to that window's folder (left literal in a window without one); the CLI starts one per run from the project, with the placeholder left literal. So the plugin's entry runs the launcher's `--mcp` mode with `--root "${workspaceFolder}"`, and the launcher passes the root to `jevmem mcp` when it is a folder and leaves the server on its working directory otherwise. In a project that is not turned on the server lists its tools and answers every call with one line saying jevmem is not turned on there: no request, no file, no `.jevmem/` folder (tested).
- A plugin rule with `alwaysApply: true` is in every chat of every project the plugin is installed for, so the rule is short, **588 characters of body, 96 words, about 147 tokens at four characters a token** (`results/cursor-rule-cost-2026-10-19.json`; the 0.7.4 rule was 1,287 characters), and its first sentence keeps the agent off jevmem where the project has no `jevmem.config.json`: no tool call, no request. `jevmem init --tool cursor` writes the same text now.
- **In the app, on 2026-10-19 with Cursor 3.26.9** (the probe's hooks in three windows, five turns typed by hand; Cursor's Hooks output channel): every plugin hook fired as a project's does, from the plugin folder for every event but `stop`, which ran from the project root; a plugin's MCP server started the moment each window opened its folder, with no toggle, and the agent called its tool without an approval step beyond the plugin itself; a plugin's rule reached a chat in a project without jevmem (it does not show in `beforeSubmitPrompt`'s `attachments`, a project rule does); and with the real plugin copied to `~/.cursor/plugins/local/` beside a project set up with 0.7.4's files, the plugin's hooks ran and stood down (one `cursor-plugin-standdown` line) while the project's hooks decided the turn once. One trap of the `agent` CLI: with several plugins that have hooks, the `CURSOR_PLUGIN_ROOT` environment variable a hook gets can name another plugin's folder (the e2e's copy of this plugin read the probe's manifest through it, [the run](../results/e2e-2026-10-19-v076-cursor-plugin.txt)), while the placeholder in the command text is substituted per plugin; so the launcher reads its own manifest next to its own path and uses the variable for nothing.
- Cursor also imports the plugins installed in Claude Code from a marketplace (those in `~/.claude/plugins/installed_plugins.json`; the directory's synced install is not among them) and runs their Claude-format hooks with its own payloads; it reads their MCP servers from an `.mcp.json` file only, never from the manifest, so the jevmem Claude Code plugin's server does not start in Cursor, and its four hook commands do nothing with a Cursor payload (every captured payload replayed through them: no output, no request, no file; `test/cursor-plugin.test.ts`).

**What the launcher does for the plugin.** `--plugin <event>` runs `jevmem hook --cursor --plugin`, with the plugin's version from its own manifest in `JEVMEM_PLUGIN_VERSION`, and on `sessionStart` writes `~/.jevmem/cursor-plugin` (the version and the time, once a day, in any project): the one file the plugin keeps outside a project, and how `jevmem init` and `jevmem doctor` know it is installed on this computer, since Cursor records installs in its own state. In a project that is not turned on the hooks answer at once and run nothing, as the project hooks do. **Beside a project's own jevmem hooks** (a project set up with 0.7.4 or 0.7.5) the plugin's hooks stand down, with one log line a day (`cursor-plugin-standdown` in `.jevmem/log.jsonl`), so a turn is decided once, by the project's hooks; a turn's conversation-and-turn mark is the second guard. `jevmem doctor`'s `cursor` line names the plugin, the day it last ran and the stand-down. **`jevmem init --tool cursor` with the plugin on this computer** turns the project on and writes no Cursor file, saying so; `--files` writes the hooks, the launcher, the MCP entry and the rule anyway (a teammate without the plugin), and the plugin stands down beside them. **Moving a project over** to the plugin alone: `jevmem init --remove-hooks` removes the five entries and the launcher as before and, while the plugin is on this computer, jevmem's rule file when its text is one jevmem wrote and the `jevmem` entry of `.cursor/mcp.json` when it is the one `init` wrote (a changed rule and other servers stay); then reload the window.

**Measured on the plugin's build.** 0.7.4's Cursor held-out set (`eval/cursor-heldout-sessions.jsonl`, 24 turns; used by 0.7.4's measure, so this is a regression check on that set, not a new held-out result) replayed once through the build: 24 of 24 turns paired whole, decide right on save or skip for 21 of 24 and on kind for 20 of 24, every saved line with its labelled words (14 of 14), the one reversal superseded, the same turns as 0.7.4's second run ([results](../results/cursor-heldout-2026-10-19-v076.json); the dev set 26 of 26 and 23 of 25, [results](../results/cursor-dev-2026-10-19-v076.json)). Fix d, Cursor's own follow-up line ("Briefly inform the user about the task result…", which Cursor submits after a background task ends) **after** a turn has ended, is read as that turn's tail now and decided with nothing: 0.7.4's live check had decided it as a turn of its own (two requests, skipped); the one captured chat with that shape is the fixture (`test/fixtures/cursor/app-followup/`), and the held-out set's example, inside an open turn, was folded already. What the e2e `cursor-plugin` scenario and the live checks measured is in the CHANGELOG entry.

### What the hooks actually receive

Observed on Claude Code CLI 2.0.30. `Stop` carries **no message text**; jevmem reads the last user and assistant turn from `transcript_path` (JSONL). Some newer versions document `last_assistant_message` and `user_prompt`; both shapes are handled. On Claude Code 2.1.281 (2026-09-28) the `Stop` payload also has `prompt_id`, `background_tasks` (each `{id, type, status}`, a subagent `running` while the main agent stops mid-turn) and `session_crons`, and the transcript never holds the main agent's final text when the hook runs: it is only in `last_assistant_message`. Since 0.6.0, jevmem adds it to the turn read from the transcript (until then it was used only when the turn had no other text).

```json
{"session_id":"…","transcript_path":"~/.claude/projects/<slug>/<session>.jsonl","cwd":"/your/project","permission_mode":"default","hook_event_name":"Stop","stop_hook_active":false}
{"session_id":"…","transcript_path":"…","cwd":"/your/project","permission_mode":"default","hook_event_name":"UserPromptSubmit","prompt":"your prompt text"}
```
